# 伴星 AI 味的原因定位 · 2026-10-08

本轮能确认的发生环节是当前 DeepSeek 调用链的**正文生成**：输入中的事实和更正完整到达客户端出网，但生成仍把普通分享写成解释、评估和帮助，并补充没有来源的细节。最有证据的行为解释是默认帮助型回答与日常接话目标不匹配；这不是对模型内部训练机制的证明。

尚未证实唯一底层根因。没有直接原厂同模型与 Go 的同协议比较，不能把“当前通道默认这样回答”进一步断言为模型权重、Go 增加隐藏指令或某个服务参数造成。返回的模型名也不构成权重证明。前面的复现与候选淘汰应称症状定位和改法筛查，不能说已经找到根因。

## 本轮填补的两个诊断缺口

此前温度消融的实际模型为 `gpt-6-luna`，轻思考也是 Luna，另一思考对照是 `qwen3.8-flash`。此前 DeepSeek 的 bare/protocol/full 和连续接话诊断一直固定 none / 0.9，不能把别的模型的失败结果外推为 DeepSeek 参数无影响。

对原六个诊断前缀固定同一 DeepSeek、Go Responses 端点、原生消息、32 字身份和完整输出声明，新增四模式共 24 次：none/0.9、none/0.2、low、high。none 两档只改温度；low/high 只改思考档。none 与思考档比较同时包含温度字段按档案省略，不能称纯思考单变量。

再新增六次，只从 none/0.2 中删去最后的 32 字“书房里的 AI 伴星”身份。实际出网没有任何 system 消息、instructions、人格、示例、时间线或业务上下文。简历与练琴两项还各只有一条 user，无历史可供模仿。

所有 30 次上游返回模型标识都是 `deepseek-v4.1-flash`。none 推理 token 为 0，low 为 69–290、high 为 44–692，证明响应确实进入了不同推理模式；没有保存生成的隐藏推理。DeepSeek 原厂文档说明 Responses 的 none 关闭思考、low/high 开启，温度在思考模式无效；客户端现有省略行为与之对应。[原厂 Responses 说明](https://api-docs.deepseek.com/api/create-response/)、[思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)。这些文档不能证明 Go 内部完整处理过程。

## 观察与可得结论

| 被核对的假设 | 实际观察 | 结论范围 |
| --- | --- | --- |
| none / 0.9 单独导致失误 | 0.2、low、high 仍出现心理归因、辩解和无依据细节 | 本批同类失误不依赖这一种配置；未测重复，不报稳定胜率 |
| “AI 伴星”身份导致所有问题 | 无任何系统输入时，拉链分享被写成四段心理分析，还说“小事、不值得庆祝” | 角色身份并非这些失误复现的必要条件；有身份时仍可能改变篇幅、语气与错误形态 |
| 旧助手回复带偏了全部交流 | 无历史的练琴输入被写成“背后一定是反复的卡顿”，补“手指的酸”；无历史简历输入被接成修改/投递流程 | 模仿旧回复不是所有失误的必要条件；有历史时仍可能放大问题 |
| 应用没传到当前事实 | 原生输入和实际 wire 逐字一致；模型采用“布料挪出来”后又解释用户为什么不兴奋 | 本批客户端完整传递事实，生成采用事实后仍扩写推测；不证明整个项目不存在其他上下文问题 |
| 客户端指定与上游返回模型名不一致 | 30 次请求名与响应名一致 | 没发现标识错位；不能据此证明实际权重或排除网关处理 |

去掉身份后的接水回复仍推测用户边读故事边喝水、一杯不够。四种模式中接水还分别补热水、杯子已喝一半、用户忘了喝、还没坐下歇等细节。它们不是用户提供的事实；问题不能仅用禁用某一个口头禅解释。

更正与抱怨中，回复常采用新操作信息，随后替上一条评价重新找理由。能复述更正不等于把旧解释彻底撤回；这属于输出选择和对话更新不完整的可见行为，未读隐藏推理，不推断模型内在动机。

## 排查方法与验收口径修正

前面多轮补示例有局部作用，但未取得稳定收益，继续同类泛调不能冒充查因。本轮没有新增人格候选或改正式配置。

自然度也不能只按“有没有建议、有没有反问”判断。贴题关心、问题和小建议可能自然；应区分关心与接管、试探与武断归因。尤其“眼睛疼”之后的简短休息关心，单独出现不能自动证明 AI 味。过长的分析、替人安排完整流程、贬低或评价能力、补编活动/感受仍须单独判定。先前两候选也存在无依据操作/亲身经验等独立失败，本轮没有将它们重新判成合格。

当前应用靠自然语言要求生成遵守事实与交流边界；引文核对只保护明确引文，不能认证自由正文中的普通断言。人格字段提供名字、口味和风格，运行策略提供软指导，都不能构成语义正确性的硬保证。这是已核对的实现限制，不等于证明必须增加规划、审校或更换框架。

## 快速追加：接口与第二条既有网关

用户要求尽快再核对。源码检查显示，Go provider 将已有 system 合并为 instructions；无 system 时不增加身份。公共 HTTP 层将 body 序列化后发送，未发现另加角色指令的代码。客户端源码检查不能读取供应方的隐藏处理。

[Go 官方接口表](https://opencode.ai/docs/en/go/)给 DeepSeek V4.1 Flash 列的是 Chat Completions，当前项目统一使用 Responses。这是值得检查的兼容路径差异，但不直接证明错误。

新增三组、六个可观测请求：同 Go、同 `deepseek-v4.1-flash`、同原生文本、无系统提示、none/0.2、384000，两条路径均非流式 JSON。分别核对拉链更正、简历和练琴。两边都扩写心理/过程或后续安排；Chat 路径没有显示内容改善。所有上游返回标识匹配请求，推理用量为 0。两协议的请求形状、关思考字段与会话 ID 不同，未作严格的纯端点因果结论。

再通过已配置的 tokenrhythm 网关核对简历/练琴两项，使用原厂当前 `deepseek-flash` 别名。[DeepSeek 发布记录](https://api-docs.deepseek.com/updates/)将该别名指向 V4.1 Flash，[网关模型页](https://tokenrhythm.studio/models)列出这个 DeepSeek 来源别名。本次是同版本声明的通道诊断，没有筛选其他模型或修改正式路由；未证明网关实际权重与 Go 完全相同。

第二网关也给简历分享提供冷读、检查和投递流程，给练琴分享作疲惫解释。两个网关/接口报告的简历输入均 17 token、练琴均 16 token，输出声明与温度相同，实际推理为 0。单个前缀每条件一次，不能报总体胜率，也不能完全排除网关因素；但进一步不支持“Go 专属处理导致全部现象”，证据更偏向当前 Flash 默认的帮助型回答。
