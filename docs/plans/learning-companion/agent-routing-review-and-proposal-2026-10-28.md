## 1. 建议确定的方向

**保留一个原生 Agent 执行循环，把“理解目标、选择工具、读取结果、调整下一步”交给模型；宿主只承担权限、协议、真实状态、可靠交付与恢复。快慢调度最多决定计算资源，不决定用户任务必须走哪些工具。**

不把“规则 → 向量 → 分类 → 固定执行 → 文本审查”作为新的默认链。历史里这条路线的大部分组件已经试过；此次补测也没有验证出可直接上线的快路由。

实施顺序确定为：**先建立并通过 Agent 能力基线，再选快慢调度，最后验证整条产品链。** 不引入新的向量阈值；第二轮只保留窄职责 few-shot 作为资源调度候选，具体模型/端点配置仍未获得生产准入。这里缺的是通过验收的具体配置，不是又一张架构图。原生循环只是必要结构，当前模型在该结构中能否胜任仍需验证，不能从 Claude Code / Codex 的形式直接推导能力。

必须撤回本次此前准备接入的“全量语义入口同时挑工具、提取消息数量、生成可复用回复”的上线建议：它扩大了前置判断的职责，又重走了旧 hybrid 的部分路径。保留实验和代码现场，后续实施时单独拆除或替换，不能直接发布当前脏工作区。

## 3. 本轮新增真实模型实验

使用当前配置的 `mimo-v2.6-flash` 和实际 Pi provider，合成材料，不操作真实账户。固定 24 个场景、每场景 2 次：闲聊、引用、否定、假设、简单事实、短创作、多轮接受/换话题、读取、改写、记忆、独立气泡、图片指代、因果、证明和混合请求。

先固定策略及评判标签，再将两种提示交错随机排列，最多 2 个并发；答案标签不进入输入。两臂都只分类，不生成给用户的答案。后续用同一简短提示开启思考做对照，未根据失败增加例句或词表。

| 条件 | 路由标签符合预设策略 | 应进处理档却进快档 | 决策中位耗时 | 样本 P95 | 最慢 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 简短 fast/agent JSON，关闭思考 | 42/48 | 6/24 | 0.956s | 4.855s | 7.393s |
| 同时分类、选工具、提取消息数量，关闭思考 | 39/48 | 6/24 | 1.479s | 5.094s | 7.686s |
| 简短 fast/agent JSON，开启思考 | 37/48 | 8/24 | 2.706s | 10.384s | 23.381s |

这是 **144 次分类调用**，另有 **2 次出网载荷检查**。第二臂另有 2 次解析/适配错误和 1 次返回对象没有合法 route；思考臂有 3 次对象没有合法 route。工具目录臂的 39/48 只检查路由标签，不代表其工具名和其他字段全部正确。

具体反例：偏好记忆、独立气泡发布被判 fast；工具目录臂出现合法别名 `companion_memory_save`，但同时返回错误的 fast 路由及未声明的 `toolUse=write`；开启思考的某次接受保存请求返回了一整段无关的笔记内容。没有真实执行这些输出。因果/证明的 fast 判定违背实验预先定义的资源策略，**不能据此单独断言其最终答案必错**。

注意：旧 wire helper 只从 `instructions/messages` 提取提示哈希，没有读取 Responses 的 `input` 中 system 消息，因此显示空串哈希。额外 2 次载荷检查确认提示实际在 `input[role=system]` 中；原始提示和 SHA-256 已另存。空哈希是观测缺口，不能解释成“模型完全没收到提示”，也不能假装对前 144 次逐条完成了完整出网正文核验。

结果边界：

- 这是短合成上下文的请求级诊断，没有 HTTP、队列、真实工具执行、客户端或语音；时间是完整路由决定可用，不是正文首字。
- 有 24 个独立场景，不是 48 个独立场景；思考臂是后续诊断，不是独立留出集；并发与提供方负载会影响时间。
- 不能据此给所有分类器或模型下永久结论。它足以说明：**本轮这三个候选均不具备直接上线依据**。结构化输出能挡格式错误，挡不住合法 JSON 中的错误 fast 标签。
- P95 用 nearest-rank，中位数用样本中位数，失败保留。小样本分位值不是线上 SLO 保证。

## 4. 为什么一直在反复

**一是把多种故障归成“意图不准”。** 历史里有资料没有传到模型、图片历史丢失 assetId、执行对象缺失、工具协议、等待/取消、消息交付、事实与推理错误。换分类器解决不了这些。

**二是分类结果承担了不应承担的权力。** 从一个标签扩展到指定工具、强制读写、判完成、决定是否丢弃已经落库的结果。上游理解一错，下游只能照错路走；复杂目标也不等于唯一工具序列。

**三是评测与真实目标错位。** 22 条黄金集从 15/22 调到 22/22，说明旧样本适配改善，不足以证明新表达泛化；向量路由又把 LLM 标签当真值；包含正确关键词的错误回答也曾通过自动检查。更多绿灯没有解决这个问题。

**四是性能比较混了口径。** 分类时间、首个网络事件、礼貌开场、真实答案、第一份落库成果不是同一个指标。旧实现还叠加分类对冲、两份草稿、正式重跑和修复，所以“一轮调用很多次”的问题不只来自 token 数。

**五是配置来回变化而缺少能力准入。** 先关思考求快，再靠 deepen 补质量；漏工具后加预读，误判后补否定词；最后又全开思考或加前置分类。这是在弥补尚未被证明具备的模型能力。

## 5. 推荐架构的职责边界

| 层 | 负责 | 不承担 |
| --- | --- | --- |
| 上下文装配 | 当前原话、角色、材料 ID/版本、图片引用、正在执行/已完成/已取消的真实任务状态；历史来源与必要压缩 | 用指代词、短句长度或上一轮标签猜授权；只拼最后 2–3 轮就丢掉更早相关依据 |
| 原生 Agent 循环 | 结合上下文决定回答、查资料、调用工具、澄清、继续或完成；工具结果进入同一循环 | 按分类器给出的固定步骤执行；缺一次工具就永久封死该类任务 |
| 计算档位 | 经验证的模型原生自适应推理优先；若实际服务不支持，再评估独立、窄职责的快慢调度 | 同时生成答复、挑工具、解析槽位、指定必须有几个回执；输出权限或“任务完成”结论 |
| 工具与状态 | 权限、参数、版本、幂等键、确认、真实成功/失败/未知结果，及时交付已成成果 | 根据“删/改/搞定”等自然语言词自动执行或补执行 |
| 交付与恢复 | 结构化成果引用真实回执；已经公开的内容不重复发布；未知写入先核对 | 凭模型说“完成了”认定完成；凭任意一个成功写入认定复合任务全部完成 |

需要强调两个限制：

1. 计算档位误判仍会伤害质量。保留完整工具能力能降低“路由错就根本做不了”的后果，但不能保证关闭思考的模型一定主动补救。因此快档必须单独验收，不能拿工具仍在当可靠性证明。
2. 回执校验不能发现所有“没调用工具却口头说已完成”。它能验证显式引用是否真实，不能替代语义理解。任务模型需自行维护来源于当前请求的目标/产物记录，逐项对照结果；宿主只核验客观存在、版本与归属。未请求的动作、遗漏的目标仍需端到端语义评测，必要时评估有明确触发依据的任务完成复核，不给所有闲聊追加审稿模型。

工具契约可以要求“修改需要对象 ID 和当前版本”，这是数据正确性的前置条件。不能把“凡是提到笔记都先搜索再读取再修改”写成通用流程；已有授权且版本有效的对象可直接使用，搜索和计划由模型决定。

## 6. 具体推进顺序和停止条件

### 第一步：冻结基线，分开验证路由和 Agent 能力

选定一个源码版本、模型/端点/协议/思考配置、提示与工具面，保存 manifest。旧提交、当前工作区、容器实际版本分别记录；不能一边测试一边修改热加载代码。

建立三类对照：

- **能力对照**：测试器事先选择合适计算档位，执行模型只见用户输入、资料和可用工具，不注入答案或工具顺序。先确认“没有路由错误时，Agent 本身是否会做”。
- **原生自适应对照**：只对真实支持该能力的端点测试，同一 Agent 直接处理。当前 MiMo 的 `none` 和思考开启是两种行为，不能把 low/medium/high 当成三个已有效区分的档位。
- **调度对照**：在能力对照通过后，再加入一个资源选择器；其他变量保持一致。比较完整任务成功率与等待，而不是只比分类准确率。

准入失败时，先定位是输入/协议/工具合同还是模型输出；修复一类有证据的原因后在新样本验证。若模型在正确档位和完整证据下仍达不到任务质量，下一步是评估实际可调用的模型/端点配置，不能用词表继续遮盖。历史试过的失败配置必须带上原结果，不重新当作未知候选。

**本步骤交付物：**可以运行同一原生循环的快档和质量档能力报告；可以是同一模型不同档位，也可以是不同模型。没有通过就不进入快路由发布。

### 第二步：只保留有净收益的速度优化

首选已经通过测试的模型原生自适应能力，省掉独立分类往返。若现有可用端点无法同时满足，则保留同一循环，实验独立的资源选择器；本轮三个分类候选均不直接采用。

检索/线性头仅作为后续资源调度候选：独立标注、上下文感知、分组留出、弃权机制；不得自动把自身/旧 LLM 标签追加成真值。top1–top2 必须按不同类别比较；margin 不是概率，不能替代分布外检测与校准。先证明高精度下的覆盖和端到端收益，才值得加入基础设施。

并行只在前述质量门槛通过后实验：最多一份待发布的真实快速答案与窄资源判断并行。路由未落定时不发布答案、不执行推测性写入；需要工作时丢弃私有草稿，进入同一 Agent。相比旧“双草稿 + 分类对冲”，必须有明确的调用数、丢弃成本、取消传播和尾延迟收益。不是默认立即启用项。

**停止条件：**拿不到独立验证的质量收益，或等待/费用变坏，就淘汰该组件；不用改失败样本期望、加专用词表、反复重跑取最好结果继续推进。

### 第三步：沿真实产品链验收

冻结已通过的配置后，经 HTTP→队列→worker→实际工具→数据库→事件→客户端验证。只使用隔离合成账户执行写入；线上失败取最小必要脱敏材料做回归，不回放真实写操作。

至少包含：聊天→任务→聊天；同一句“好啊”在不同上下文；引用/假设/否定；多意图与部分完成；历史图片重新读取；新笔记中随机秘密值；读过后版本变化；临时与长期偏好；消息气泡数量；取消、断线、重启、写入结果未知；长上下文与后台负载。

对成果检查实际内容与副作用，不要求唯一工具序列。少调用正确工具是收益；为了迎合预设流程多调用工具不算更可靠。

## 7. 验收口径

沿用方案 58 的目标作为待达成标准，不谎称已经达标：普通聊天**有效正文**首字 p50≤2s、p95≤5s；代表性常规请求完整达成率≥95%。如果用户要求 p95 也≤2s，需要单独证明提供方自身的尾延迟先满足预算。

| 维度 | 必须记录 |
| --- | --- |
| 分类诊断 | 应进质量档却进快档的比例、快档实际覆盖、弃权/格式错误；同时给分母，不只总体准确率 |
| 内容质量 | 当前问题是否回答完整、事实/推理是否正确、引用及说话人是否正确、是否额外虚构或擅自安排 |
| 工具与成果 | 真实状态变化、目标/版本、所有要求的产物、未要求的副作用、重复写入和部分完成 |
| 延迟 | 排队、上下文、调度、提供方首个正文、首份真实成果、完整交付；成功样本分位值与未完成率并列 |
| 稳定性 | 提供方失败、协议错误、宿主错误、用户取消、被新请求接替分别统计；不把主动取消等同技术失败 |
| 费用 | 实际发出请求、取消请求、可得 token 用量；拿不到取消用量就报下界，不虚构节省比例 |

建立开发集、校准集、冻结留出集，按语义场景/会话家族拆分，同一场景改写与重复不能跨集。旧失败进入回归集；一旦用于调提示就不再是盲测。内容检查使用客观材料与明确评分点，模型评审仅辅助；争议样本保留人工/逐条审阅意见。

验证“漏入快档小于约 1%”不能靠几十次绿灯：即使假设独立同分布，约 300 个相关独立样本零错误才接近单侧 95% 上界 1%；同一句重复 300 次不成立。现实多轮和场景聚类需要按家族报告，不以这一估算冒充线上保证。假保存、错误对象修改和未授权副作用为验收阻断项，零观测不等于永不出错。

速度公式也必须如实：串行调度约为 `排队/装配 + 调度 + 生成首字`；安全的并行发布至少要等 `max(调度完成, 可发布正文到达)`。中性开场或“收到”只能计确认反馈，不能计有效回答首字。当前证据不支持保证每次 1–2 秒。

## 10. 第二轮后的明确取舍

采用单一原生执行循环，入口只调计算资源；保留完整相关上下文与工具能力，由模型理解目标并自主操作，宿主核验对象、版本、真实回执、幂等和恢复。few-shot 的 56/60 含 4 次超时，未观测到错误放行，但只是 30 种新措辞各两次，不能宣称生产可靠性。

不采用全量 none（假保存、未读编造）、全量 high（仍有逻辑错与尾延迟）、全量语义入口生成答案/挑工具、kNN 新阈值、默认并行草稿或中性开场充首字。本次并行＋1.2s 截止试验没有通过速度目标，独立复核只保留为质量任务实验。

实现优先级已经确定为：真实工具合同与状态核验 → 精简强制流程提示并固定能力配置 → 窄资源调度的完整链验收；提供方正文尾延迟与推理质量作为独立准入项。当前不能保证 1–2 秒或 ≥95% 完整任务成功率，不能发布工作区里的语义入口候选。详见第二轮报告的逐条证据、限制和验收门槛。
