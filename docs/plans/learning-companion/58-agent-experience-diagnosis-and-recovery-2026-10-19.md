# 58 · Agent 速度、质量与稳定性整改方案

日期：2026-10-19；时区：Asia/Shanghai。

**用户最新要求：速度、质量、稳定性。速度同时包括实际耗时和感知等待；进度展示是必要能力，需要与执行提速一起交付、一起验收。** 本文据此重排此前方案，保留已取得的实际证据。这一轮仅更新诊断与方案，没有修改运行代码，也没有完成发版或部署。

## 1. 三项验收目标

| 目标 | 用户需要的结果 | 必须覆盖的改造与验收 |
| --- | --- | --- |
| **速度** | 尽快得到有效回答和成果；等待期间及时知道在做什么、推进到哪里。 | 同时缩短实际耗时和感知等待：减少无效模型往返与执行绕路；及时呈现真实进度；已完成成果立即可用。分别记录首个明确反馈、有效正文首字、首份成果、完整交付耗时及不明原因的空等区间。 |
| **质量** | 回答当前问题，正确、完整，符合要求；让它做的事真实完成。 | 核对话题与对象、事实依据、数量、篇幅、内容完整性和真实产物。模型正常返回、格式正确和工具调用成功，都只是其中一部分证据。 |
| **稳定性** | 多次使用、长时间使用和异常情况下都可依赖。 | 常见请求重复执行不频繁报错；停止、重试、断线恢复、后台完成和切换话题行为一致；不重复写入，不丢已完成成果，不把未知结果宣称为成功。 |

三项同时验收。提速不能靠减少用户要求的内容或降低正确性；提高成功率也不能靠拒绝原本支持的常见请求。每次增加分类、审查或重试调用，都需要证明对这三项的收益和代价。

## 2. 已确认的问题与证据边界

前一轮检查了真实 Electron 开发窗口 `localhost:5173`，打开实际对话手记并展开既有任务过程，同时以只读事务查询本地开发数据库。审计没有发送新消息、发起新模型调用、修改笔记或设置、部署服务。

[原始基线](../../testing/agent-experience-baseline-2026-10-19.json)保留三个选定既有运行的事件时间、步骤状态、模型审计与工具回执。它们是问题样本，不能推算生产总体错误率。服务端事件时间也不等于画面呈现或人耳听到声音的时间。

| 样本 | 实际结果 | 对三项目标的影响 |
| --- | --- | --- |
| “生成几篇中国历史的笔记吧”，`b89f998b` | **46.4 秒后失败**，`REPLY_FORMAT_INVALID`；只成功搜索笔记，后两步均遇到格式错误。 | 速度、稳定性：等待后仍无交付，格式恢复未解决问题。此次没有重建供应商原始异常输出，具体协议错误仍需定位。 |
| “生成几篇历史笔记给我”，`31cfbf06` | **263.8 秒完成**；65.9 秒出现首个思考事件，83.7 秒出现首个工具事件，263.8 秒才出现首个回答增量。 | 速度：实际耗时长；早期已有后台活动，但默认折叠使用户难以感知推进。 |
| 同一次笔记请求 | 一个模型步骤耗时 **78.9 秒**，随后三次创建笔记因“工具组未装载”被拒；之后装载工具并重新生成，最终保存三篇笔记。 | 速度、稳定性：已生成的操作与当前可执行能力不匹配，造成高成本绕路。 |
| 同一次笔记请求 | 三次成功建笔记的账本区间为 **177 / 321 / 254 毫秒**；最后工具事件后约 **54 秒**才最终答复。 | 此样本的主要等待落在模型、编排和末尾交付；已完成成果应及时出现。这些账本区间不是独立数据库性能基准。 |
| “讲个400字左右的温馨睡前小故事给我吧”，`0a62eb2d` | **12.3 秒完成**，正文首字约6.7秒；持久化文本仅 **114 个字符**，含标点，仍标记成功。 | 质量：结构完整或模型成功返回，没有保证满足用户要求的篇幅。不能用这种缩短回答来宣传提速。 |
| 真实手记窗口 | 外层过程默认折叠，展开后每段思考和工具步骤仍默认折叠；摘要单行截断、对比度低，过程区还有独立滚动。 | 感知速度：信息存在，但难以及时看到和理解，用户仍处于空等。 |

`31cfbf06` 的持久计数为8步、4工具、12模型调用；界面显示5次工具，工具账本有7行（含拒绝），模型审计有11行（含取消的分类对冲）。这些计数采用不同口径，尚未形成清楚可核对的说明，不能将它们等同为有效工作次数，也不能把取消的对冲直接算作用户可见失败。

观察到的 worker 使用 `hybrid`，通用 provider 超时为900,000毫秒，未配置伴星单独覆盖；任务默认没有整轮墙钟截止。检查时容器文件与工作区文件一致，不足以证明历史运行当时加载了哪个模块版本。

## 3. 速度：实际提速与感知提速一起做

### 3.1 缩短真实执行与交付时间

- 在已知任务的具体操作生成之前，准备相应的已授权能力。修复“要求创建笔记，候选操作为空，生成完再因缺工具被拒”的绕路；自由表达仍保留授权范围内的能力发现。
- 拆分统计分类、上下文装配、模型生成、工具执行、协议修复、结果核对和末尾总结的耗时，针对真正昂贵的步骤修改。不得将所有慢都归给模型或数据库。
- 已保存的笔记立即提供真实标题与打开入口，后续任务继续执行；完整成果可用后，不被额外总结步骤继续阻塞。
- 清理重复内部纠正和不相关任务背景，记录上下文各部分的必要性与体积。样本输入约从23,000增长到38,500 token，值得实测比较，但不能据此直接认定某次答错的原因。
- 模型、思考档位、传输方式和任务编排都是被测变量。使用同样请求、资料、输出要求和负载比较，分别报告时间、质量与失败；不预设当前模型一定足够，也不预设换模型必然改善。
- 后台反思、主动参与考虑、嵌入和语音等工作与前台请求核对资源争用，避免后台负载拖住正在等待的用户。

### 3.2 用真实反馈减少感知等待

**进度展示属于速度目标的必要部分，优先级与执行优化并列。** 用户应及时得到确认，持续理解实际推进，尽早使用已完成的部分。

| Before | After | Why |
| --- | --- | --- |
| 泛化的“正在执行工具”长期不变。 | 显示真实对象、阶段、已用时间和最近确认进展，例如“正在写唐朝笔记，已保存1篇”。 | 用户能够理解等待对应的工作与推进。 |
| 过程和步骤两层默认折叠。 | 当前过程与可读工作说明默认展开，历史查阅可直接读到关键过程；保留用户手动选择。 | 不需要逐层点击才能知道它在做什么。 |
| 等最终模型总结才看到全部成果。 | 每份已保存成果立即出现真实链接，余下部分继续推进。 | 用户更早获得可使用的结果。 |
| 延迟、重试和失败都像同一种转圈。 | 依据真实信号区分生成中、等待服务、正在恢复、失败和结果待核对。 | 降低不确定性，让用户知道是否需要操作。 |

输入后立即产生操作反馈；服务端接受请求后呈现明确的真实处理状态。阶段更新及时出现，文字与成果保持可读，避免跳动、自动折回或强行滚动打断用户。

进展暂时没有变化时，显示最近已知活动及持续时间。可先以10秒提示间隔、30秒明确说明延迟作为界面试验值；它们是展示策略，不是强制结束任务的时限。只在确有重试、切换或完成时显示对应状态，不编造阶段、百分比或预计剩余时间。

工作说明帮助理解目的、方法和依据，工具回执证明实际读写。沿用已有可展示信息，不为进度额外采集隐藏推理。长技术参数可以作为次级详情，但当前步骤、工作说明、错误、待确认事项和成果必须可直接阅读。停止和恢复操作始终可达。

**速度验收分开记录并共同判断：**

- 实际速度：有效正文首字、首份真实成果、完整交付耗时，按任务类型报告中位数和尾部等待。
- 感知速度：操作反馈是否及时、首个明确工作反馈何时出现、最长不明原因空等区间、阶段变化是否可理解、成果是否及时可用；结合真实窗口连续操作评价，不能只凭有一条状态事件判定通过。

## 4. 质量：以满足当前要求为准

- 保留唯一权威的当前请求、材料与版本引用；转交、内部纠正、压缩、恢复和换话题都不能把旧问题变成当前问题。
- 现有工作区已包含纠正消息去重、新建笔记路由与分类器候选修复，实施时保留这些改动，再验证实际入口闭环。[此前调查](../../testing/learning-artifacts-live-probe-2026-10-19.md)记录过内部重附用户原话导致“你重复说了几遍”的误判，以及后台目标只交付摘要、实际没有创建笔记的问题；本轮没有重新独立复现这些生产事件，不能把已有修复记录当作部署后验收。
- 内部纠正必须保留宿主身份。现有带标记的重附件仍使用 `user` 角色，需要验证模型是否稳定地区分真实用户发言与内部修复。
- 固定检查当前对象、问题各点、篇数、近似篇幅、结尾完整性、事实依据和实际保存结果。大幅不符合要求的回答即使格式正确，也算质量失败。
- 解释、创作与执行分别评价。教学不能遗漏关键条件；故事不能只有开头；创建笔记不能仅在总结里写“已完成”。人格和语气服务内容，主动补充不承担原本应在本轮完成的后半段回答。
- 使用真实口吻、多轮指代、否定、混合要求、只读权限等样本验证路由。分类器黄金集只能提供部分证据，还需完整阅读请求、回答及产物。
- 必要时针对确实不完整的结果接续修复，不给所有聊天一律追加阻塞式审稿模型；新增调用必须有质量收益与等待代价的比较。

## 5. 稳定性：让恢复基于真实状态

- 分开处理网络故障、非法工具协议、参数错误、缺失工具组、资料过期和写入结果未知；避免同一错误在多层重试机制中反复绕行。
- 每类失败明确恢复归属，沿用同一运行、检查点与操作身份。重试前记录改变了什么；成功部分保留，未完成部分继续。
- 写入结果未知时先查回执和业务状态，再决定重试；已经保存的笔记不能因后续模型失败而丢失或被重复创建。
- 单独评估交互请求首输出与无活动超时，不直接沿用15分钟通用超时处理所有场景。取消必须传播到实际模型与工具，最终状态持久化；单纯慢不等于应中断正常长任务。
- 保留此前不按任意步骤数、工具数或模型调用数截断任务的决定。完成、明确停止、真实故障和没有推进的证据决定后续处理。
- 停止后新请求可正常继续；断线或重启恢复同一任务；旧回复和后台完成不覆盖当前话题、输入、焦点或声道。
- 后台目标只有在取得所需真实成果后才可宣称完成；任务列表关闭时，完成结果也能按既有参与与通知规则送达。
- 备用模型、重试与断点恢复必须在实际配置下测试。短样本成功和单元测试全绿，不等于持续使用稳定。

## 6. 实施顺序：每次交付都检查三项

| 顺序 | 实施范围 | 可核对的结果 |
| --- | --- | --- |
| **第一批：修通现有高频失败，并同步给出进度** | 用“创建三篇历史笔记”贯通正确能力、真实进度、逐篇保存与即时链接、格式错误恢复、停止和部分重试。验证并保留已有局部修复。 | 同一真实窗口完成客户端→API→队列→worker→权威保存→事件→客户端；既减少绕路，也能清楚看到推进；三篇内容符合要求，重试不重复创建。 |
| **第二批：实测比较提速与质量优化** | 对高耗时模型步骤、重复生成、上下文和最终交付逐项改造；比较模型及思考配置，补充请求完整性评价。 | 同样请求和输出要求的前后对照，同时给实际耗时、感知等待、内容评价和失败记录；回答变短不能算提速。 |
| **第三批：连续使用与版本验收** | 长对话、后台负载、断网重连、服务重启、未知写入结果、换话题与迟到消息。 | 实际构建客户端和运行服务的版本可核对；多次重复与长会话通过；保留负面样本，再由真实体验确认。 |

不以整体框架重写或独立展示样机作为前置。过程界面与真实执行共用现有运行身份和事件流，避免新增另一套任务状态机。

## 7. 验收方法与初步目标

以下是建议目标，尚未实测达成。先建立固定请求、输出要求、版本与后台负载的基线，再校准阈值。

| 目标 | 初步验收要求 |
| --- | --- |
| 实际速度 | 普通聊天有效正文首字p50≤2秒、p95≤5秒；固定的三篇短笔记样例首篇保存≤30秒、完整交付p95≤90秒。长材料研究和大型交互产物单独分组，不混算。 |
| 感知速度（速度的一部分） | 反馈及时，当前步骤和工作说明无需展开；阶段、延迟、恢复和已完成成果连续可读；不让用户长时间面对含义不明、没有解释的静止状态。用真实窗口与连续操作核验。 |
| 质量 | 代表性常规请求完整达成率以≥95%为初步目标，公开分母和失败样本；验收集内不允许假保存、假完成、明显答非所问或遗漏关键要求。 |
| 稳定性 | 正常请求重复与长会话验证；异常注入下无重复写入、已成结果丢失、错误对象修改和旧回复覆盖；停止、恢复与后台完成状态一致。技术失败率和恢复成功率单列统计。 |

保留用户实际失败作为固定案例：新建笔记、换说法重试、约400字完整故事、故事续讲、笔记解释、聊天→任务→聊天、内部纠正不虚构用户重复。加入长笔记、资料版本变化、未装载工具组、非法模型输出、流中断、一篇保存后失败、未知写回执，以及关闭任务列表后的完成送达。

每类正常样本重复运行，并做持续多轮会话。尾部耗时需要足够样本，不能用几次成功证明稳定p95。超时、取消、被新请求接替和无正文运行保留在结果表中；有效完成时间与未完成比例一起报告，避免只统计成功的快速样本。

学习卡测试按方案57的新笔记归属合同接入，不恢复已删除的旧复习、旧制卡或学习轮次作为前置。本方案也保留方案56默认主动参与能力，不借可靠性整改改变这项产品决定。
