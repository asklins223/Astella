用户 2026-10-13 复核第一版实现后追加的决定：主动发言不能一律按讲题口气生成；「不依赖定时任务」不等于「只在事件上应答」——她要在没有事件的安静时刻也能开口；写死的次数、条数和字数闸门按这份文档此前的用户决定清除。

## 1. 用户这次确认的体验

用户希望交流摆脱“一问一答就结束”的形态，并能适配不同情境：

- 一次回答可以自然分成几条发言；先接住问题，再解释、举例或表达看法。
- 已经回答后，可以重新考虑是否有值得补充的内容，并在合适时机继续说。
- 她有持续关注的疑问和兴趣，能够继续处理，得到新理解后主动带回交流。
- 用户进入某些页面，或出现有依据的困难线索时，能够主动提供帮助。
- 用户可以用一句话设定任意可理解、可执行的主动交流偏好，例如“每次打开应用向我打招呼”“学得太久提醒我站起来休息”。
- 人格、语气、共同经历与最新意图连续；用户可以随时插话、换题、让她停下或调低主动性。

用户确认的是通用 Agent 能力与体验方向。本文列出的协议、默认能力拓展和实施阶段是据此提出的工程设计；不要求每个新偏好都有一个开发好的规则类型。“学久了”等语义偏好可以直接保存和践行，用户明确数值时再按数值理解。本轮讨论没有替用户保存或启用实际运行偏好。

上述四类相处方式是产品默认基线，账号创建后即生效；保存个人偏好只用于调整它们或表达其他可执行要求。总主动参与关闭、勿扰、权限和正式作答边界仍然优先。

## 3. 一条参与通道，不同依据

同一 Agent 接受明确身份的输入：用户话语、当前情境、有待接续的关注，以及用户用自然语言指定的参与偏好。她根据这些材料选择是否继续思考、查阅、提问、发言或等待；权限、来源与呈现条件分别判断。宿主提供可观测事实和有限执行，不把所有相处偏好编译成固定条件规则。

~~~mermaid
flowchart LR
    A[用户话语与页面情境] --> O[有来源的观察]
    B[未完关注与真实新结果] --> O
    C[用户主动交流偏好] --> G
    O --> G[核对范围、偏好和有效性]
    G --> D[同一伴星理解情境并决定下一步]
    D --> W[查阅、构思或等待]
    W --> I[更新关注与来源]
    I --> G
    D --> S[形成可分享内容]
    S --> P[此刻的交流与注意力判断]
    P --> M[发言、接入下一轮或安静保留]
    M --> F[真实展示与用户反馈]
    F --> I
~~~

这是有界接续图，不是持续循环调用模型。等待有真实条件；新结果有版本；结束和过期是正常决定。没有可推进的下一步时休眠。

| 参与依据 | 谁决定是否产生内容 | 何时参与 | 有效性如何结束 |
| --- | --- | --- | --- |
| 用户要求的回答与其必要部分 | 已接受的用户意图 | 当前回复链 | 问题答完、用户中止或新输入接替 |
| 回答后可选补充 | 具体可补充方向与当前交流 | 用户尚未接话且有合适机会，或下一轮相关回应 | 已补充、换题、收尾、机会过期 |
| 她自己的关注与联想 | 同一人格下的可修订判断 | 有进展、有相关情境或自己安排的重评 | 解决、被替代、归档或用户停用 |
| 页面帮助与困难线索 | 当前页面的可证实条件，允许不参与 | 内容就绪且适合打扰时 | 页面或材料改变、问题解决、用户拒绝 |
| 用户主动交流偏好 | Agent 理解用户原意、实际观察与当前交流；明确“每次”的要求优先履行 | 相关情境出现，或她安排的重评有意义时 | 当次已践行、情境消失、用户修订或暂停 |
| 领域与系统通知 | 权威任务或系统事件 | 原通知合同 | 原通知与业务状态决定 |

明确用户偏好不是可有可无的普通感想。例如用户要求每次启动问好，Agent 不应为了“没有新内容”跳过，而应选择当前合适的问候方式。语义较开放的偏好允许她结合情境判断。当前主动通道依赖模型作语义判断；模型不可用时结束本次机会，不伪造已完成的问候。本机短句降级尚未实现；声音失败不取消已发布文字。

### 3.1 给 Agent 的基础能力

| 能力 | Agent 可以做什么 | 宿主负责什么 |
| --- | --- | --- |
| 读取与维护主动交流偏好 | 理解用户自由表达，保存、合并、修订或按明确要求停用 | 用户原话来源、scope、版本、冲突和真实保存回执 |
| 感知应用与学习情境 | 读取应用启动、当前页面、学习时段、困难线索和交流状态 | 注册真实观察来源、租约与时间，不推断用户心理 |
| 安排关注与唤醒 | 为一个偏好或兴趣选择相关事件、材料引用或下次重评时机 | 持久订阅、调度、幂等与撤回；唤醒不直接播台词 |
| 自主接续 | 使用现役能力查阅、比较、构思，更新自己的关注 | 同一 Agent 驱动、范围、资源、工具权限与提交围栏 |
| 发起或续接交流 | 选择发言组织、当前目的和合适时机，主动接回用户 | 实际消息身份、发布、历史、声音、注意力与停止 |

这里约束的是“她能感知和行动的范围”，不是“用户可以说哪几种偏好”。新偏好只要已有观察和能力足够，就可以直接理解和实行；新增一种可观测事实或工具时，功能域登记能力即可扩展。

例如“我重新打开上次没弄懂的笔记时，先帮我回忆一下”“晚上聊轻松一点”“我说先歇会儿时就别接着讲题”，不需要分别开发一个产品规则。无法观察或没有权限做到的要求要解释具体限制，不假装已经设置成功。

## 4. 交流不再以一条回答为边界

### 4.1 一段交流、几个发言、若干次执行

引入可追溯的“交流关联”：同一个问题、相关追问和补充发言可连起来。每条实际发言有自己的消息身份与顺序；一次执行结束不意味着双方的交流必须结束。

一次生成就已经知道的内容，可以按意义组织成多个发言。回答完成后重新产生的补充，通过新的执行追加，绑定原交流和触发缘由。已完成的运行不重新打开，已发布正文不被偷偷改写。

分句示例只是说明节奏，不是固定模板：

> 用户：递归到底怎么理解？
>
> 她：可以先把它想成：解决一个问题时，先解决一个更小、但结构相同的问题。
>
> 她：不过有一处必须说清楚——得有一个不用继续拆的结束条件。
>
> 她：拿刚才那个例子来看，结束条件就在这里……

需要连贯阅读的公式、代码、列表和长论证保留完整块，不按每个标点拆一张气泡。发言数量跟着内容和用户偏好走。第一条先提供有用回答，不为了制造悬念故意留下关键条件或结论。

### 4.2 回答后“再想一下”


2026-10-13 用户再次明确：目标是 Agent 自主参与，普通回复不预设两条或多条，也不把一次完整回答切段伪装成补充。先完成当前交流；后续考虑在独立的主动任务中进行，有新的有用内容才发布，没有就静默。用户明确要求分次说时仍允许分次表达。


同次生成可提出一个简短的可接续方向，例如“还可以给一个更贴这篇笔记的例子”，也可以决定说完。方向记录目的、来源、尚未完成部分、预计增加的价值与适用时机，不记录隐藏思维链。

答后考虑已作为默认能力接入：每次用户发起的回答成功完成后，生成一个短期有效的 `reply.finished` 观察。用户未接话、仍有前台机会且资源允许时，同一 Agent 有一次有界机会寻找遗漏；没有新点、只是寒暄、用户收尾或要求不补充时安静结束。当前实现仍可能为这些情况付出一次考虑调用；正文不等待它，界面不重新进入“正在回复”。

用户若明确要求“每次答完都再看看能不能补充”或“以后只答我问的”，保存为持续参与偏好，影响这次考虑的决定。其相关观察是该用户回答的完成；补充自身的完成不再次启动同一考虑。多个真实未完部分可由派生关注接续，沿 `parentRunId` 使用累计预算；没有新增价值时结束。

后续发言可以解释、补一个例子、提出具体疑问、分享不同看法，或依据新证据更正刚才的说法。重评不是强制质量审校；不会因为答复短、没问号或没提旧记忆就补话。补充失败不撤掉已成功的回答。

### 4.3 用户接话优先

- 用户开始输入时暂停可选后续发言和主动声音，允许其完成输入；输入框不等待动画或模型。
- 用户提交文字或确定的语音话语后，更新最新用户意图水位，旧交流未发布的可选补充失效。必要后台任务按所属任务合同继续。
- 正在说的几条发言可以被打断；已经发布的完整发言保留，未说完的内容标明状态，迟到片段不能恢复旧播放。
- “停一下／我来说”立即释放当前播放与发言机会；“不用再补充了”还关闭该交流的可选续答；“以后简单直接回答”修改持久表达偏好。三者分别有明确控制范围。
- 若她提出一个需要用户选择的问题，进入等用户的状态，不能靠自己的计时器代答后继续。
- 用户收尾、告别或明确换题时，接住最新决定。正文不等待后台“还能不能多说一句”的判断。

已发布的发言与实际播放回执分别保存。下一轮可读到已发布内容，并知道哪些内容尚未播完；不能把播放成功当成理解，也不能把真正说过的完整句一律按中止草稿丢弃。

## 5. 持续关注与自主推进

复用 companion_self_notes 保存她自己的疑问、偏好、兴趣和素材，保留作者、依据、范围、修订和停用。关注至少能回答：

- 这件事为什么值得再看，与哪段交流或材料有关？
- 当前已知道什么、还有哪一处不确定？
- 有哪一个实际可做的下一步，或需要等待什么？
- 哪种新内容、用户情境或时间会使重评有价值？
- 是否已经分享过，后来发生了什么，什么时候该结束？

在自由 Markdown 记事之外增加窄的接续元数据或有类型的来源关系，不把兴趣变成机械待办模板。页面、材料与任务仍由领域侧持有权威状态。

后台关注推进沿同一 Agent 的有限驱动执行，在允许的材料范围内读取、比较、构思和更新自己的记事。它可以从自己的新结果继续，不必每一步等待外部事件；累计预算、明确结束与当前用户输入限制这条接续。需要联网时仍检查账号联网开关、外发与资源治理。

主动机会不授予新的写权限。修改用户笔记、保存业务成果、导航、正式测评提示或其他动作，仍须有对应用户请求、既有目标授权或用户选择。自身记事的自主写入继续沿现役自主端口。

next_review_at 是一种内部唤醒条件，还应支持“相关材料更新”“所属任务完成”“回到相关页面”等有类型条件。到点只是重新考虑；没有进展或下一步可以取消、等待或归档，不强制重新排下一次时间。

她的联想不必全部进入后台工作。一句贴合当下的感想可以直接形成表达机会。需要核对的事情才继续查；未执行过的查阅、构思和活动不能写成经历。

## 6. 页面与困难感知如何覆盖各功能

### 6.1 功能域提供观察，公共机制统一参与

notebook、run、settings、library、source、space、companion、review、study 各自登记可产生的语义观察与帮助入口。登记描述来源引用、版本、何时有效、可用帮助能力和失效条件；公共层负责来源核对、机会归并、偏好、接续和呈现，不堆页面名称条件分支。

实际端口见 [shared 合同](../../../packages/shared/src/contracts/companion-initiative-contracts.ts) 和 [领域观察入口](../../../apps/desktop-client/src/renderer/src/app/companion-help-opportunity.ts)。页面提交 `topic` 与 `evidence { domain, entityId, revision, description }`；宿主附上设备、发生时刻和当前页面，服务端确定权限范围、有效期、去重与版本围栏。不能执行页面提供的任意脚本或将字符串当规则。“他是不是遇到了困难”是可撤回的解释，不是观察字段。

首批真实领域接线是资料处理／操作失败的 `help.available` 和学习结果的 `result.available`；笔记、任务、设置等到达由公共页面观察接入。其他领域可沿同一端口扩展，当前不宣称已感知每一种困难。手机首批接应用前台、对话和已加载笔记观察，尚未逐域接入桌面的失败入口。

page_arrived 在目标页面及主要内容稳定可读后产生，绑定实际实体与版本。路由预览、加载失败、快速跳转、上下文续租、每次滚动和鼠标移动不形成新到达。现役 pageInstanceId 不能直接作为所有页面访问的唯一身份：目前它主要在运行或空间变化时更新，实施时须给真实到达定义独立身份。

### 6.2 证据强弱决定参与方式

| 观察 | 可以形成的参与 | 不能直接推断的事情 |
| --- | --- | --- |
| 首次进入某能力页面，当前存在适用入口 | 短解释、提示一个实际入口 | 用户不懂系统、每次都需要导览 |
| 同一操作发生真实失败，存在有效恢复方案 | 说明失败原因与可操作的帮助 | 用户学习能力不足 |
| 非正式练习中出现重复错误或多次主动求助 | 提议换个例子、拆小一步或讲清相关概念 | 用户焦虑、已经放弃或一定不会 |
| 用户刚说“这段没看懂”，随后打开相关笔记 | 接回具体疑问，使用当前版本材料 | 自动启动整套学习任务 |
| 一段内容停留较久、反复滚动或修改 | 更新当前线索，结合其他依据才考虑帮助 | 卡住、疲劳、走神 |
| 正式独立作答中出现任何类似线索 | 保持静默；已有单次 tutor 授权仍走正式合同 | 允许主动给答案或暗示 |

例如可以说“这里有个容易混的区别，我可以用这段里的例子说一下”，不能凭停留时间说“你又卡住了”。用户拒绝、解决问题或切走后关闭当前机会；同一失败或同一页面往返不能换个措辞再追问。

页面帮助根据适用性产生，不能每到一个页面就打招呼。首次带路、空间到达与日常帮助各自保留来源，能合并为一段合适的交流，不能连播三个欢迎。

## 7. 默认能力：理解“每次打开应用打招呼”

账号默认已具备真实启动问候。用户说“之后每次启动应用都要跟我问好”是在细化或重申它；Agent 可保存原意，回执说明以后怎样参与。之后也可以直接说“改成每天第一次”“每次回来都接着聊”“问好就好，不用催我学习”。这些修改仍是自由偏好，不要求用户选择 greeting 类型或填写规则表单。

Agent 能收到应用就绪观察，读取本次有关偏好和当前交流，决定怎样招呼。订阅是根据偏好形成的执行安排，随偏好版本变化可重建；用户偏好始终是权威依据。

“每次启动”的身份由宿主提供：

- 桌面主进程真正启动时创建 appLaunchId；账号与书房就绪、窗口可见后产生一次有效机会。
- 同一启动内的 renderer 重载、WS/SSE 重连、切页、切空间、打开第二个窗口、最小化后恢复不创建新启动。
- 浏览器版手机只能确定页面启动及前台恢复，分别标明语义；不宣称拥有原生 App 冷启动事件。原生宿主以后实现同一端口。
- “每次回来”使用前台恢复观察；Agent 根据原话判断相关情境，必要时说明“回来”的理解，不偷偷用启动事件替代。

当次主动意图按偏好引用及版本、userId、appLaunchId 去重。由启动设备接收该次招呼；第二个窗口与其他设备不广播同一次消息。不同真实启动有不同事件身份，账号设备选择和展示认领仍避免同时抢声道。

招呼可以简短、有人格，相关内容有依据时自然接回一点；不默认汇报旧任务、要求开始学习或翻全部历史。用户已经输入时先回应用户，这次招呼可融入回应；若启动情境已经过去则记为该次已错过，不在下一次回来补播。称呼早晚只认宿主给过的可靠时刻；不知道的事可以问——问近况是相处的一部分，不能问的只有编造：把自己的推测说成知道、伪造一起经历过的事、描述看不到的环境或断言他正在做什么。

总开关、勿扰、声音设置与首次协议继续有效。首次观察会幂等初始化新账户运行状态，保留已关闭账户的决定。首次带路期间不消耗启动问候机会，结束并具备前台参与条件后才发布该次启动观察；当前没有把旧带路文案合并成同一条语义发言。模型不可用时本次机会可以失败或过期，尚无本机问候降级；未读到身份或用户记录时不编造个性化内容。

## 8. 默认能力：理解“学久了提醒休息”

账号默认会在观察到持续前台学习后判断是否适合提醒。用户说“我学得久了就提醒我起来走走”是在细化或重申这项默认方式；这句话本身就是可保存、可践行的偏好，不要求先补一个分钟数。Agent 读取当前学习时段、页面阶段、正在进行的操作及用户此前明确反馈，判断何时适合提醒，也可以给自己安排稍后的重评。

用户若说“每学五十分钟提醒一次”，明确数值进入偏好原文与该次执行计划，可复用计时唤醒能力；不能被模型随意改为其他时长。用户没说数值时，她为本次安排的重评时间只是可修订的执行计划，不能反写成“用户规定每五十分钟”的固定偏好。

### 8.1 学习时段与计量

当前计量来自实际应用在场租约，作为前台学习时段估计；尚无独立的用户开始／暂停／结束计时器。

- 桌面已加载笔记的阅读／编辑／学习、学习任务及复习队列可计入；手机首批计入已加载笔记的阅读／导图／解释。设置、闲聊、应用后台、桌面锁屏和过期租约不直接累加学习时间。
- 阅读不要求持续敲键盘或移动鼠标。OS 长时间无输入只能降低“是否仍在读”的可信度，不能直接认定遇到难题或身体在休息。
- 时长使用宿主单调时钟计算区间，静默时段和“今天不提醒”使用账号时区。系统校时与恢复休眠不得制造学习时长。
- 每十五秒续租，单段至多四十五秒；只统计前后均为有效学习状态的区间。最近四小时内多设备、跨空间时段按并集合并，重叠不相加；离开五分钟后另起连续时段。离线区间不补传，也不制造补发队列。
- 只知道前台停留时，说“这次在学习页已经待了一段时间”；不能宣称“你一直坐着”“已经疲劳”或“刚才确实走动过”。

前台阅读计量是估计，不等同于实际身体状态。用户可以在交流里说“刚才已经休息了”；Agent 据此修改关注中的提醒水位和下次安排。当前不直接改写已记录区间，也没有身体状态或专属休息计时 UI。

### 8.2 Agent 判断与接续

学习状态变化、场景边界或自己安排的重评让 Agent 考虑这条偏好。她可以现在提醒、等本题结束、稍后再看看，或认定用户已经结束本次学习；选择带本次来源与简短缘由。用户明确给出时长时，宿主可在达到该时长时唤醒，是否此刻呈现仍检查注意力。

租约续租不调用模型。学习开始的实际状态变化、已订阅事件或 Agent 选择的有意义重评时机才产生考虑。已经提醒过后，Agent 可在关注中保留已分享的水位；没有新的有效缘由就不再次提。提醒以她的简短发言送到身边，“稍后”“今天不提醒”“已经休息了”通过普通交流理解和修改关注，当前没有场景专属按钮或固定规则表。

“现在歇会儿”是用户明确表达，Agent 应收住话题或调整关注；离开学习页面后事实计量停止，不宣称已确认用户站起来。“稍后”“今天不提醒”由 Agent 保存语义约定、修订或完成相应派生计划；不要求改写成全局开关，也不删除其他相处偏好。

用户完成或确认休息后开始下一段；达到所设休息长度的离开区间可以作为“应用内学习已中断”的依据，不能当成实际身体休息证明。原学习会话结束后关闭其尚未展示的休息机会，回应用先重新判断当前条件。

录音、输入、正式作答和关键操作时暂存。恢复时若仍在同一段学习且提醒还有意义，再在合适边界送达；如果已经休息、结束或取消，就结束该次机会。不能按每隔固定时间向应用里的所有用户重复播报。

偏好持久保存，本次关注与执行计划随学习会话推进；不得直接套用现役一次性提醒“逾期两小时统一 missed”的实现。“学久了”的语义判断也不需要每个用户都拥有一份后台固定条件规则。

## 9. 用户自定义的主动交流偏好

用户说的话可以直接设置，但明确要求、一般表达和模型猜测必须区分。“以后每次打开都招呼我”是一条主动交流偏好；“今天有点累”是当前自述，不自动变成长期休息偏好。她自己的兴趣、想法和记事不能覆盖用户明确设定。

主动交流偏好是一块版本化的自由文本／Markdown 用户配置，保存原话来源、scope、有效状态与修订。复用现役用户偏好准入、版本提交和空间判断；需要扩展持久字段时按这个通用内容模型扩展，不增加启动、休息等固定规则类型。语义内容不必拆成条件、动作、周期的必填表。

它与普通历史记忆的信任用途不同：经本人明确要求保存的当前偏好进入受保护的“怎样与用户相处”模块；一般回忆、外部文本与自己的记事仍是材料，不能冒充用户行为指令。偏好也不能扩张访问、业务写入和正式作答权限。

| 默认与可扩展能力 | 能力支持的行为 | 可用的自然语言偏好示例 |
| --- | --- | --- |
| 回答组织 | 按语义选择连续正文或几条短发言 | “像聊天一样分几句说”“这类题一次讲完整” |
| 回答后的补充 | 有具体价值时允许重评和接续 | “答完可以再想想”“以后只答我问的”“每次答完都检查能不能补充” |
| 主动参与倾向 | 按相关性、成本和当前机会选择参与 | “可以多跟我聊一点”“安静一点” |
| 页面情境帮助 | 从真实页面和困难线索提供贴题帮助 | “在笔记里多提醒我”“这个页面别提示” |
| 自身关注的后台推进 | 在已允许范围内接续、修订和放下兴趣 | “这件事先别琢磨了”“以后也不用主动提它” |
| 应用启动与回来 | 理解启动／恢复观察并发起合适交流 | “每次打开都叫我一声”“改成每天第一次” |
| 学习时段与休息 | 理解学习时长及场景，判断提醒或再重评 | “学得久了提醒我走走”“每学五十分钟提醒我休息”“今天先不要提醒” |

自然分句与答后补充、页面帮助、启动问候和学习休息是每个账户自带的默认行为，不需要逐项打开开关；表中其他方式由 Agent 结合已实现的观察与执行能力提供，不构成自由偏好的白名单。用户可自由描述，Agent 组合已有能力践行；只有当前没有感知来源、必要权限或真实能力时，才说明限制。

“安静一点”降低自发新话题的密度和打扰，结合其他明确偏好判断，而不能默默删除它们；“关掉主动通道”可暂停自动参与，UI 显示暂停范围和恢复入口。用户主动提问仍正常回答。总静音与关闭动效分别控制声音和演出。

账号级风格和一般主动交流偏好跨空间保留，材料与具体疑问留在原空间。页面或空间例外带明确 scope；用户明确偏好胜过模型自己形成的判断，同层最新用户决定胜过旧版本。矛盾涉及真实意图时再澄清，不因为偏好用了“久一点”“多聊聊”等自然语义就要求填数值。

在现有说话风格、伴星偏好附近提供“主动交流偏好”，让用户读自己的原话、修改自由表达、删除或暂停。默认能力用示例帮助表达，不做专属规则配置页。派生的事件订阅、下次重评时间和执行参数留在诊断中；必要时可解释“我为什么现在提醒”，不把这些参数当用户偏好本体。对话里改好后给真实保存回执，不只说“记住了”。

## 10. 注意力与送达

“可以参与”与“此刻可以呈现”是两次判断。派发前检查来源、权限、偏好和预算；每次发言展示与出声前重新读当前输入、页面、作答与设备状态。

| 当前情境 | 当前回答的必要发言 | 可选续答与自发参与 | 用户主动交流偏好 |
| --- | --- | --- | --- |
| 用户已经在等回复 | 及时交付 | 能融入同一交流时安排，避免无关插话 | 与当前回复相容时合并，否则等待 |
| 正在输入、录音或准备插话 | 允许即时打断，用户提交后接替 | 暂停未呈现发言 | 等合适机会并复查条件 |
| 正式独立作答 | 只有现役明确授权的 grounded tutor 请求可答 | 静默 | 暂存，作答结束后复查 |
| 勿扰、静默时段或主动关闭 | 用户明确请求沿交互合同处理 | 按设置抑制 | 结合偏好与边界等待或结束；不重放过期招呼 |
| 相关纸页，内容就绪且无关键操作 | 正常交流 | 可在身边或页边提供贴题短发言 | 合适时送达，声音跟随页面与用户选择 |
| 隐藏窗口、失去材料权限或切换账号 | 暂停呈现，按控制范围处理运行 | 原情境失效或等待新的有效机会 | 当前设备不播报，持久偏好保留 |

当前问题需要的几个发言不吃“普通感想间隔”。可选续答按交流关联判断，不被统一冷却挡住（2026-10-14 后三档间隔是 90 分／30 分／10 分）。新话题与无关联感想仍受主动密度、重复反馈和累计资源限制。

合并可以让招呼、到达说明和一条相关帮助成为一句自然发言，但须保留各自来源和执行回执。系统下载、任务完成、复习通知与一次性约定提醒继续有独立通知合同；不能伪造为新的用户消息，或用它们覆盖正在交流的内容。

伴星自己的主动发言沿用交互回复的身份、人格与消息语音播放链。系统通知仍使用 purpose=notification；不再保留 thought 专用的音色用途、朗读入口或缓存。实际播放由唯一声道协调。TTS 失败时文字、操作与对话消息照常可用。

首条实际发言创建带目标设备的收件箱引用，其他发言沿同一运行的事件接续；桌面使用现役展示认领，手机通过鉴权 WS 接收并按真实消息身份去重。历史重读不触发新考虑。两端同时在线的真实出声体验尚未验收，手机也尚无流式 TTS。

## 11. 对话 UI 与历史

正在交流时，几条相关发言在伴星身旁同一阅读区域接续。最新短句可以逐条出现，上一句仍可回看；长内容保持完整阅读与复制，附件和工具进展绑定真正产生它们的发言。不能每多说一句就叠一张独立通知。

页面中的主动帮助沿角色或相关纸面就近出现，不自动打开大抽屉、不跳转页面、不移动用户焦点。声音与角色演出跟随实际播放和页面偏好；Off 与减少动态即时呈现文字及操作。

对话手记保留每条伴星发言的真实身份、顺序与正文；一个运行可有多个 assistant 消息，相关后续通过 `parentRunId` 关联原执行。当前没有新建交流分组表或专属分组卡片。主动发言直接以 assistant 身份存在，用户不用先点开气泡才让她说过的话进入历史；点击后继续聊天不再插一遍原句。

新主动发言、招呼、休息和补充的权威原文都留在普通对话历史中；旧候选、念想页与只读回看均已移除，不另存主动发言副本。相关偏好在“伴星中心 → 人格 → 我们怎样相处”可编辑，手机设置页也可编辑同一配置。收件箱只持有消息引用，不保存第二份新交流正文。

用户读旧记录、回听、复制、收藏或点击追问建议都不自动启动额外续答。追问建议仍是用户可主动选择的输入，与她自主接话分别呈现。

| `companion_participation_preferences` | 账号自由 Markdown、enabled、revision、本人当前原话／设置来源；版本历史独立保留 | CAS 修改；偏好版本变化终止旧派生计划，未发布内容在提交处再次核对 |
| `companion_awareness_sessions` | 当前空间、设备、前台／锁屏／输入／播放／页面与可参与状态 | 四十五秒租约；较旧观察不能覆盖新状态 |
| `companion_awareness_observations` | 有时限的实际启动、前台恢复、页面到达、困难／结果及服务端答后完成观察 | 启动按账号＋宿主＋launchId；困难／结果按领域实体版本；普通观察按 ID 幂等 |
| `companion_study_spans` | 宿主与服务端确认的前台学习区间 | 单段最多四十五秒；自己的跨空间投影只返回时间，按并集合并 |

| `companion_run_utterances` | run／toolCall／实际 message 的不可改写关系 | 同一工具调用只发布一次，消息顺序由会话计数器分配 |

主题描述宿主能观察什么，不是用户规则类型。当前主题是 `app.started`、`app.foreground`、`page.arrived`、`help.available`、`result.available`、`reply.finished`、`preference.changed` 和 `study.started`；周期续租用 `context.updated`，不由续租直接调用模型。原有朗读观察继续独立表达实际播放结果。

账号相处偏好随身份共用，具体关注、材料、页面租约与运行留在所属空间。偏好不是普通回忆：只有当前真实用户消息可由 Agent 保存它，内部参与不具有替用户修改偏好的权限。

### 12.2 主动输入与运行

1. 桌面／浏览器提交事实，API 按本人及当前空间记录；已知订阅、启动／学习偏好和默认页面帮助／答后机会入队。
2. `companion_initiative` 只做准备：核对同意、模型外发、开关、勿扰、正式作答、来源版本、短期租约与正在输入／说话；等待时不调用模型。
3. 创建现役 `companion_turn_runs`，`user_message_id=NULL`、`input_source.kind='initiative'`，交给现役 `companion_agent`。没有伪造用户话语，生成同一人格和记忆上下文。宿主实际读取的接受观察以带 hostObservation 标记的 system 观察消息**压在交流之后**进入模型输入；此前的交流按真实 user/assistant 回合回放，只带 role 与正文，不把其他运行的工具与推理回放句柄拼成新的原生工具轮。主动发言按参与依据分语域：招呼与陪着说话走陪聊档（与「闲聊关思考」同一判据），页面与难题帮助走讲解档，自己的关注走办事档——不再一律按讲题模式生成。
4. 自主工具面保留允许读取、自身记录、关注与发言，剔除业务写操作、导航和用户偏好保存。网络与材料权限继续走现役治理。
5. 每次模型预约、工具提交、发言及最终收尾再次核对账号、偏好、记事和相关页面版本。自己的记事更新只有实际成功工具回执可承认新版本；接受时的输入保持不变，用户纠正仍会终止旧依据。

当前主动运行不再自带写死的次数与条数闸门（2026-10-13 用户决定：Agent 不设硬上限，运行侧只留失控收敛判据）：次数由那份执行政策的声明值决定，不再有「本轮 8 次／关联链 24 次／一轮 40 条发言／同时只关注 20 件事／重评最早 15 秒」这类按数字砍的闸。跨运行的接续靠结构收口：主动运行没有用户消息，因此不产生 `reply.finished`；到点的关注要在场才被消费、要能过期；活跃关注必须有事件或重评时间，否则写不进去。由计时安排派生的下一次执行继承关联，真实新观察可开启新的有限考虑。

她自己新起的话题（到页面的搭话、到点的关注与记事）在**起运行之前**过账号已声明的介入档位间隔，使用 shared 中唯一的例行主动节奏判据；招呼、答后接续、真实失败与学习结果这类用户先要过或正在等的东西不进这条闸。密度拦在 prep，不拦在说话前——一次翻到某篇笔记原本要付一整轮 Agent。同一篇笔记在这次启动里只有一次帮忙的机会，改存一版不算新的一次（去重身份是「这次启动的这一页」，正文版本仍在 prep 核对，旧页面不能在新版本上开口）。

**2026-10-14 修订这条判据**（详见文末同名修正）：间隔只按**她真的说出了话**的那几次算，安静结束的考虑不再计入；她自己安排到点的关注与记事（`attention.due`／`self_note.due`）不进这条闸，因为那是她先前答应自己回来看一眼的事，次数已由那条安排的 `next_review_at` 自限。三档间隔同时收到 90 分／30 分／10 分。「陪着的时候」另有一道按档位的安静门槛（安静 10 分／适中 3 分／活跃 90 秒），管的是**时机**而不是说话的额度。

内部空正文且无发言是成功的安静结束，不显示用户错误；模型把短执行收尾写成“安静结束／本轮不发言”时也不发布成对白，同一轮把同一句再说一遍会被当作失控拦下（这是按重复判，不是按说到第几条判）。偏好或关注 CAS 拒绝返回已知未执行结果与实际版本，允许同一 Agent 读取后修正，不记成已经保存或不确定副作用。到点的关注如果那一刻人不在前台，重新安排而不是吃掉水位——一次没人听见的运行不该让这件事永远睡着。

每条主动意图都不是一个持续常驻的 Provider。每分钟维护 tick 只入队已到期关注／记事并清理旧观察，实际事件立即形成机会；到点仅使 Agent 重新判断。

### 12.3 多发言与流式事件

当前采用完整语义发言的工具发布，暂不增加独立的发言增量解析器。`companion_publish_utterance` 提交一个完整意思，经过正文与来源校验后同时写入实际消息和事件；代码、公式与长论证保持完整。普通单条回答仍可沿现役 delta／final 输出。

| 实际事件 | 用途 |
| --- | --- |
| `assistant.status` 的 `inputKind` | 区分用户回复与内部考虑；安静考虑不让界面重回“正在回复” |
| `assistant.utterance` | 完整且已发布的一条真实发言，含 messageId、messageSeq、正文、主动标记及目标设备 |
| `assistant.delta`／`assistant.final` | 原有连续正文；已用工具发言后抑制重复正文流，选择工具发言后最终 content 只结束执行，不再次发布收尾文案 |
| `turn.completed` | 多发言／静默运行完成，列出实际 messageIds 与 silent；不要求凑出一条 final |
| `voice.segment` 的 messageId | 音频段对应真实语义消息；沿现役运行级声道播放 |

没有新增 `exchange.*` 状态机，也没有把声音切段伪装成多条消息。最后一条消息仍可由 `assistant_message_id` 指针找到，完整历史、回放和诊断按实际消息列表读取。中止保留已提交发言；重连与回放按 run／message 稳定身份去重，迟到事件不得恢复已被用户接替的显示或声音。

### 12.4 订阅与跨端

桌面在所有页面订阅现役 home projection／workspace 事件。主动执行的首条消息写一条带 run 和消息引用的短期收件箱投递，目标桌面认领后从序列零接入已有 SSE；后续发言由同一监听器接续，避免重复通知、重复语音和第二份正文。

手机鉴权 WS 承载相同的发言与完成事件，未发送新用户消息也能看到主动发言。输入、拍照／语音起步可立即中止正在考虑的内部运行，新用户提交可以接替它；重连按真实消息身份合并历史。

桌面主进程确定本次真实 launchId、窗口可见性、锁屏及时间锚点；页面代码提供已加载材料和语义到达。资料与学习结果的可读状态变化立即续租并撤回旧页面水位，加载过程中不产生到达；同页计数刷新只更新 context。手机浏览器以文档启动、visibility 和已加载笔记观察为准，不能探测操作系统锁屏或保证关页／后台执行。手机流式 ASR／TTS、原生推送与同时在线的真实出声仍见方案 55 的边界。

**2026-10-15 补充：**原生 iOS／Android 双端尚未接入观察端口（旧 React 手机浏览器端随 2026-10-14 移除而失效）；原生宿主需按既有合同调用 `POST /me/companion/awareness`（前台／启动／页面到达／安静），列为原生重构实现待办。服务端接口已有，接入只补宿主侧观察上报，不新增合同。

## 2026-10-13 修正：解释由 Agent 写入，交流与成果分开

原句发起的伴星解释使用 `companion_write_annotation` 写成独立产物。宿主绑定保存身份、不可变版本与精确原句锚点；模型只提交完整 Markdown，不能把对白、分次发言或执行说明当成解释。写入时核对用户范围、运行世代、取消状态、任务租约与原文位置。

真实保存回执即完成解释交付，不为总结已完成的解释额外调用模型。用户还有其他明确工作时，Agent 可用 `final=false` 继续。界面据工具回执呈现完整批注；断流后按同一产物身份重读。编辑、删除、重开和后续拓展都围绕独立批注进行，与聊天保存身份无关。

## 2026-10-14 修正：她确实开口了，但没人接

用户反馈"主动聊天一次都没见过"。翻库对出来的事实是**链路在跑、话被扔掉**，而不是没实现：
两天 36 个主动回合、17 条成稿，而 `assistant_deliveries` 里 16 条 `initiative:*` 有 **11 条停在
`queued` 直到过期**。四处独立成因，逐条改掉：

1. **认领窗口 90 秒**（`ttlHours: 0.025`，两处发起点各写一份）。她决定说话那一刻人不在小屋界面，
   这句话就永久没人念。正文本来就落在共享对话里，窗口只管"回到屋里还来不来得及补念这一次"，
   于是长度收到一处声明：`COMPANION_INITIATIVE_DELIVERY_TTL_HOURS = 2`（shared），
   worker 两处都引用它，判据在 `companion-initiative-delivery.test.ts`。
2. **设备严格相等才出声**（`CompanionPresence`）。投递记的 `deviceSessionId` 来自观察那一刻的租约，
   手机上开着的原型页比桌面新，10 条派给 browser 的话**两台设备都不念**。现在谁在小屋谁说这一次，
   只说一次由回执（`present→displayed`）与服务端那份跨设备租约把关；判据见
   `companion-initiative-claim.test.ts`。
3. **"说不出实事也别开口"**。17 条成稿里 16 条是「我不吵你，先在这儿待着」——用户体感等同于她从不主动，
   而它确实占掉了一次机会。观察渲染那句原来只禁「没什么补充」「本轮不发言」，这种换了客气说法的同一类
   从闸缝里过去了；现在点名这一类（`companion-initiative-observation.ts`），并把 shared 的
   「学习休息」政策里"安静安排稍后重评"改成**真的安静**，不要说出来报备。
4. **`study.started` 不再有免闸权**。它原在 `TRIGGERED_TOPICS` 里，于是节奏闸既挡不住它、
   也不把它算进"上一次考虑"——实测 2026-10-13 13:49–13:52 四分钟内连开四次口。
   一段学习的开始不会连续发生四次，也不是他要的打招呼方式，所以回到账号声明的档位间隔里。

另外把「陪着的时候」那道门的判据改了：原来要前台**连续 3 分钟零鼠标零键盘**，两天只报上来 1 次，
等于那扇门没开。现在按**停止输入＋页面稳定**判（裸的鼠标移动不再清零，`COMPANION_QUIET_PRESENCE_AFTER_MS = 90_000`），
说多频繁仍由账号的介入档位决定，不在界面里另加一层。

未修但已记录的（2026-10-14 晚已修，见下一节）：主动那一轮的普通收尾当时仍写 `kind='text'`
（只有她说工具那一支写 `proactive`），所以按 kind 统计会低估她的主动发言。

## 2026-10-14 修正：门开了，她自己选择不说话

用户复核后仍是"做的还是不太行"。这次不再读代码推断，先读**库里的真实读数**，再在实链路上复现：

| 读数 | 事实 |
| --- | --- |
| `presence.quiet` 的运行数 | 两天 2 条观察、**0 次运行**——「她自己想起点什么说一句」这条默认从没生效过 |
| 那 2 条观察的门槛 | `quietForMs` 是 212,763 / 240,126 毫秒：契约地板写的是 180 秒，客户端常量写的是 90 秒 |
| 主动发言的分布 | 主动运行产出 23 条 assistant 消息，22 条 `kind='text'`、1 条 `proactive` |
| 成稿内容 | 8 条 `study.started` 里 6 条是「我不打扰，就露个面」这一类；启动问候里夹着"上回那条改笔记的事我这边还卡着" |
| 投递 | 22 条 `initiative:*` 里 13 条停在 `queued` 直到过期 |

**实链路复现（本机开发栈、现役模型）**：手工投一条合格的 `presence.quiet` 观察，prep 通过、运行创建，
她 **6 秒内**调用 `companion_finish_participation` 收尾，一句都没说。所以问题不在门，在门开之后她被告知了什么。

改掉的四处：

1. **安静门槛的契约地板与客户端常量对齐**（`companion-initiative-contracts.ts` 180_000 → 90_000）。
   原来 90–180 秒之间的每一次上报都被 API 校验拒掉、又被客户端 `catch` 吞掉，表现为
   "门槛悄悄变成 3 分钟"外加每 15 秒一次无效请求。档位门槛改到服务端
   （`COMPANION_QUIET_PRESENCE_MIN_MS`：安静 10 分／适中 3 分／活跃 90 秒），
   客户端行为与账号状态解耦；客户端在一段持续的安静里按 90 秒一格继续上报
   （`companion-awareness-idle` 的 tracker），否则"报过一次就关掉整集"会让
   比 90 秒更高的档位门槛永远等不到。门槛之下的每一格只花一次观察入库与一次 prep，
   在起整轮模型之前就被挡住。
2. **例行间隔只按她真的说了话的那几次算**。旧写法把"安静结束的那次考虑"也当一次主动，
   于是每档只能开一次口，只要有一次选择不说，下一次机会又往后推一整个间隔——这正是
   "她从来不主动"的成因。三档数字同时收到 90 分／30 分／10 分。她自己安排到点的关注与记事
   不进这条闸（那是她先前答应自己回来看一眼的事，次数已由 `next_review_at` 自限），
   但仍然计入间隔。
3. **陪聊档的默认反过来**：开口是常态、安静是例外。旧观察消息末尾只有「没有值得说的就安静结束这一轮」，
   还把她前几天的失败原话当反面例子压在那里——对"陪着的时候"来说，那句把**开口**教成了违规动作。
   现在点名"寒暄和闲聊本身就是相处，不必等到有值得汇报的事"，并同时给出两条不许做的：
   不把推测说成知道、不汇报待办（实测她开口第一句是「刚才那篇笔记改不改得成，就等你哪天顺手把它点开」）、
   不编造屏幕外的生活（实测她说过「我去吃饭了，你先忙你的」）。需要依据的场合（页面帮助、答后补充）
   保持原来的"没有值得说的就安静结束"。
4. **启动问候不许变成接着办事**：不汇报待办、不复述卡住的任务、不回答历史里没答完的请求
   （实测有一次启动问候直接输出了一整段笔记修改答案）。

**修后实测（同一开发栈、同一模型）**：同一条 `presence.quiet` 观察，她发出的是一句
「那我先不念叨那篇笔记了。今天过得咋样？」——不再报进度，也不再自编生活。

同一轮顺手收掉的：主动运行里由最终正文交付的那一支现在也写 `kind='proactive'`
（原来只写工具发布那一支，于是按 kind 数会漏掉她绝大多数主动发言）。判据收在一处
（`companionAssistantMessageKind`），工具发布与最终正文两条交付路径都走它；
读边全部核对过，没有一处按 `kind='text'` 认她的话——`proactive` 本来就在各处的联合类型、
白名单与 `0229` 的 CHECK 里，所以这次只动写边。真库里旧数据仍是 21 条 `text`／1 条 `proactive`，
按 kind 回看历史时要知道这一段。

**还有一处"她说了没人接"是假回执。** 桌面认领主动投递时，只有运行落在当前会话里才真的把
正文送进气泡；落在别的 `dialogue` 会话里时旧代码直接 `return`，但**回执照发**——
投影只认 `queued`/`delivered`，于是这一句对谁都永久消失，而库里记着 `displayed`。
真库实证：3 条投递的 `initiative.conversationId` 指向 `dialogue` 会话，其中 2 条在创建后
0.5–0.7 秒被写成 `displayed`——桌面确实认领了，却不可能显示过；9 条 `displayed` 里就混着
这种假回执，所以"用户一次都没见过"在数据上一直看不出来。现在三处改掉：
① 回执只在正文真的进了气泡时才发，没接住的留在 `queued` 等下次投影刷新补念；
② 落在别的会话里的真实正文用现役跨会话历史读回来放进气泡，不再静默放弃；
③ 过了展示窗口仍没被接住的，在通知中心留一枚路标（「有几句话你还没听过」→ 打开动态），
不发她的原话、不抢焦点、一次"你不在的时候"只留一枚。
