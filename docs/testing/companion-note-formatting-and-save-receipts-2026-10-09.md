# 全文格式调整与保存回执修复 · 2026-10-09

用户在已安装的线上版本上报告两类现象：要求“调整下这篇笔记的格式规范，例如代码的要转成代码块，标题的要转标题”时只得到分析；改用“改一下”后出现正文替换工具完成、整轮却报引文不匹配，并另看到“保存没成功：学习服务内部出了点问题，已记录；请稍后重试”。

## 已确认的代码问题

- 分类协议列出了插入、删除、替换、表格和流程图，但没有明确区分“调整全文格式”与“仅分析排版”。动作纠正又以整轮工具调用数为零为前提，读取一次就失去了推动实际修改的机会。
- 每页正文默认 3000 字，四步预算的最后一步收起工具。多页阅读容易耗掉实际编辑空间。编辑工具序列化输入的 20000 字上限还同时计算旧正文与新正文；这不等于新正文合同允许的 20000 字。
- Hocuspocus 的 `storeDocumentHooks` 捕获保存异常后正常返回。原有上传、伴星编辑和恢复发布路径把 `disconnect()` 返回视作保存证据，没有核对落盘快照。代码风险由真实 Hocuspocus 故障注入测试重现。
- 引文比较只取工具字符串的原始表示；富文本可见文字可能被 HTML 标签打断。代码围栏里的中文引号和行首大于号也参与了引文提取。

这些问题不能证明线上那次保存错误具体是哪条数据库语句失败。截图中四页读取涵盖第 1–55 块，不能把后一个回合直接归因为“全文被截断”；工具显示完成也不能单独证明数据库已提交。

## 修改

分类版本升至 10，明确“调整、整理、规范笔记格式”要求实际编辑，“怎么调整”“只给建议”“先别改”保持查询或回答。动作纠正按所请求写工具是否有回执判断，读工具不满足修改请求；失败或结果未知的写回执不会触发自动重复修改。

正文读取可显式申请每页 20000 字，并返回各块序号、原始内容、偏移与完整性。编辑轮次使用现有八步合同上限。编辑工具总输入上限为 120000 字，新正文仍最多 20000 字、单次核对最多 100 块；正文输出声明上限覆盖较大的完整分页。多批编辑从后向前，重新读取位置；API 允许接续同一轮已确认编辑产生的版本，其他换版仍拒绝。

三个直接连接保存入口在断开后读取数据库快照，验证其包含提交的 CRDT 新增与删除，允许快照另含后续并行输入。伴星保存异常在新事务内登记失败或结果未知，避免每次 tick 重发。已保存正文后的引文失败明确说明“正文修改已保存，修改说明未完成”。引文证据同时核对原始文字与实际渲染文字，代码围栏不充当来源引文。

## 验证

- API 46 项、worker 200 项、shared 42 项相关回归通过。包括真实 Hocuspocus 吞掉保存异常、删除但状态向量不变、并行输入的快照包含关系、只读取后仍推进编辑、未知写结果不强制重试、富文本和代码的引文处理。
- shared、API、desktop-client、ai-worker 对应 `npm run typecheck` 通过，差异空白检查通过。
- 现役 `deepseek-v4.1-flash` 的八条合成分类样本全部通过：原话与五种编辑表达进入 `companion_edit_note`，三条仅咨询/不改表达没有进入编辑。
- 现役模型在合成 55 段、8423 字文档上执行两次工具调用（读取、替换），实际调用现有编辑领域函数。结果含五个真实标题和五个 SQL 代码块；渲染文字去除空白后与原文逐字相等。编辑输入 17247 字；此样本本身没有超过旧总输入上限，不能用它证明截图那次就是工具输入超限。三个模型调用共 39144ms，仅为单样本时间。
