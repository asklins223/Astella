# 账户头像、共享笔记在场与本机缓存

2026-10-09 用户反馈：账户头像换过后，共享笔记顶栏仍显示首字母；要求头像缓存本机、上传图片上限 10 MB。本次范围是账户头像。

## 实现

- `NotebookPresence` 原来只画首字母。本人印章现在读取与 HUD 账户胶囊相同的 `accountAvatar`，邮箱身份必须匹配；上传成功直接发布本次图片，清除立即恢复首字母。姓名和在读／在写保留在 title、aria-label 中。
- 主进程将头像缓存至 `userData/avatars`。对象键不可变，部署地址与用户 ID 参与缓存键，换对象键读取新图；目录上限 64 MiB，按最近读取淘汰。原子落盘、并发读取去重，磁盘失败不会阻断本次显示。上传确认后直接缓存已上传字节。
- 缓存命中仍检查头像属于当前用户，异步读取或上传期间更换会话不发布迟到结果。其他成员仍使用首字母，头像下载 API 的本人权限没有扩大。
- 共用 `AVATAR_MAX_BYTES = 10 * 1024 * 1024`，覆盖文件选择、主进程上传与读取、IPC 回执、API multipart、服务校验和直传授权。头像使用独立读取回执，避免被正文图片的 5 MB 通道拒绝。选择超限原图时在取景框前给出原因。
- 图片字节缓存从 `NoteImageStore` 抽为 `ImageByteStore` 复用；正文图片的 5 MB 单图上限、256 MiB 目录容量与授权行为保留。

## 验证

- 桌面相关 8 个测试文件、133 项通过：头像缓存、正文图片缓存、在场印章、头像文件选择边界、取景框、HUD 账户、设置页与对象传输。覆盖换图、清除、账号不匹配、重启复用缓存、迟到读取、上传写缓存及 10 MiB 边界。
- API 使用 `node --import tsx --test` 运行 storage transfer-validation、upload-security、image-pipeline-e2e：71 项通过。直传大小边界调用真实 `validateTransferPurpose`。
- shared、api、desktop-client、ai-worker 各自 `npm run typecheck` 通过；桌面与 API 在新增测试后再次检查通过。
- 本地开发服务真实 HTTP multipart 上传：3,145,728 字节和 10,485,760 字节均返回 201，读取返回 200 且字节数一致；10,485,761 字节返回 413。
- macOS 原生 Electron 开发窗口：3 MiB 蓝色测试头像在 HUD 与已共享笔记本人印章一致，本机缓存实际写入 3,145,728 字节。服务端换成绿色测试头像，设置页重新读取资料后，返回同一笔记，HUD 与本人印章一起显示绿色图，无需重启窗口。设置明确显示 10 MB 上限。点击清除后，设置预览和 HUD 立即恢复首字母，测试账号还原为原先无头像状态。
- 本机文件选择对话框的自动化未能完成原图选择，未宣称原生文件选择／裁剪／上传整条流程已走通；文件选择上限与上传成功发布图片由组件测试覆盖，上传读取由真实 HTTP 覆盖。Windows／Linux 原生窗口未检查。

工作材料在 `apps/desktop-client/outputs/avatar-cache-presence-2026-10-09/`，无会话令牌输出。使用本地测试账号；原头像为空，验证后恢复为空。临时笔记移入可恢复回收站，既有笔记正文与共享范围未改动。
