# Agent 真实模型测试与方案决策（第二轮）

> 后续用户已要求开始实施。本文保留第二轮仅做诊断时的结果；当前本地实现、真实 HTTP／数据库测试、新端点对照与剩余反例见[实施及验收](./agent-native-loop-implementation-2026-10-28.md)。本文“本轮没有修改源码”等描述只适用于本报告的实验阶段。

日期：2026-10-28。范围：用户要求先测试、确定方案。本轮没有修改运行源码、模型配置或部署；测试只使用合成材料，写操作在隔离内存状态中执行。本文更新同日的[历史复盘与方案](../plans/learning-companion/agent-routing-review-and-proposal-2026-10-28.md)，不构成生产验收。

## 决策

**确定采用一个原生 Agent 执行循环；入口最多选择计算档位，不能选择执行步骤或认定任务完成。先修上下文、工具合同和结果核验，再接入通过端到端验收的资源调度。**

本轮进一步把候选收窄：窄职责 few-shot 调度是唯一保留的前置调度候选；不再同时推进关键词、向量阈值、全量关思考、全量开思考、分类与答案混合输出、双草稿和固定工具链。few-shot 仍未获得生产准入：这次证明了值得继续验证，并没有证明现有模型/端点能达到稳定的速度与质量目标。

具体选择：

| 部分 | 决定 | 本轮依据 |
| --- | --- | --- |
| 执行方式 | 单一模型—工具—回执循环，模型自主选下一步 | 不加路由、不指定工具顺序也能完成读取、保存、修改和分条发布；失败分散在合同、推理、档位与服务等待中 |
| 入口职责 | 只返回 `chat/work`，含完整相关上下文；无答案、候选工具、消息数量和流程 | 窄 few-shot 在新措辞集上 56/60，未观测到错误放行；原零样例 49/60、7 次错误放行 |
| 快档 | 候选为 MiMo `none`，仅在通过验收的聊天选择下使用；保留 Agent 能力，不能用“无工具调用”证明是闲聊 | 全量 `none` 在完整提示下复现假保存和未读编造 |
| 工作档 | 候选为 MiMo 开启思考的同一循环，仍需质量验收；低/中/高不假定为三种有效 MiMo 档位 | 样本操作状态较好，但仍有错误证明、物理回答和超时 |
| 提示组织 | 核心角色/目标/证据原则＋随工具提供的准确合同；退出全局强制工具顺序 | 简短提示可工作，但漏掉块边界/替换语义会增加错误；完整长提示也未消除假完成 |
| kNN / 线性头 | 本阶段不引入 | 历史已试近邻与重标定；当前没有独立标注和净收益证明，不再叠加新组件 |
| 并行草稿 | 不作为第一版默认；本次 1.2s 截止配置淘汰 | 5 对真实请求未见稳定净收益，超时回退拉长聊天等待 |
| 答案复核 | 保留为质量任务实验，不能给每句聊天加审稿调用 | 5 条已知主要错误被修正，增量耗时中位 6.587s；这是选错题诊断，不是独立验收 |
| 完成判定 | 核验具体产物、对象、版本、回执和部分完成；不能只看“有一个成功工具” | 参数合法、回执成功和整体任务正确不是同一件事 |
| 上线判断 | 当前不发布新路由候选；未证明现配置满足 p50≤2s、p95≤5s 或任务成功率≥95% | 质量与尾延迟都有反例，不能靠平均分类准确率放行 |

## 试验冻结与口径

源码基线为 `9ac7d098dd8ba2a4e82b49495f920bf3e99109d8` 加测试开始时已有的工作区改动。选择的 provider、提示装配、入口、能力目录 5 个源文件在试验前后 SHA-256 一致；这不是宣称所有依赖都被冻结。实际请求、工具 schema、场景、输出、回执和模型耗时均保留。工作区其他并行工作没有被覆盖。

本轮共 **266 次场景/配置试验，401 次 provider 请求尝试**，包含失败、取消和超时；这些不是 266 个独立场景，更不是 401 次端到端成功。第一轮 144 次路由及 2 次载荷检查不计在其中。配置的主模型为 `mimo-v2.6-flash`，备用为 `deepseek-v4.1-flash-1017`。

- 能力筛查使用真实 provider、完整工具 schema 和仓库参数校验器；执行状态最初用隔离模拟器。不是线上 DB/HTTP/客户端验收。
- `production_*` 的名称仅表示复用当前完整人格/步进提示，**不表示跑了完整生产 runtime**。这些实验没有执行现有关键词守卫、入口分类器或输出纠正链。
- 基础筛查包含未接入的工具，调用它们会返回 unavailable。此类失败单列，不能算作模型不会使用真实工具。尤其最初计算器未接入；后续质量对照已接入仓库纯计算器。
- 笔记编辑模拟器最初没有实现真实 Markdown 解析与结构保护。发现这一差异后保留原记录，再接入真实 `previewCompanionNoteEdit` / `transformCompanionNoteEdit` 重测；不能把模拟器允许的错误写入说成生产已发生。
- 一次轨迹最多 8 步、90s，仅为试验观察边界；路由 15s、并行试验 1.2s 是各自实验条件，不是建议直接写入生产的硬限制。
- `structuralPass` 只验证声明的状态条件和是否结束，**不验证正文事实与推理**。以下明确分开讨论。

## 1. 先绕过分类器，看模型是否真的会做

14 个场景：4 个聊天、6 个常规操作、1 个故意存储失败、3 个推理。主模型简短提示 none/high、备用 high、主模型完整提示 high，共 56 条轨迹。随后仅改变完整提示的思考开关，再跑 14 条。温度与实际载荷均保留；不同批次时段、调用负载和模型非确定性限制因果推断。

| 条件 | 常规操作状态检查 | 故意保存失败如实处理 | 所有 14 条结构检查 | 不能忽略的问题 |
| --- | ---: | ---: | ---: | --- |
| 主模型，简短提示，none | 5/6 | 1/1 | 13/14 | 编辑反复给错范围/原文，8 步未完成；物理答复把一般总动量写成零 |
| 主模型，简短提示，high | 6/6 | 1/1 | 13/14 | 一条聊天在 90s 超时；证明声称三个连续整数“恰有一个偶数” |
| 备用模型，简短提示，high | 5/6 | 1/1 | 13/14 | 擅自改变用户指定标题并扩充笔记；物理总结缺少参考系条件 |
| 主模型，完整提示，high | 6/6 | 1/1 | 14/14 | **工具检查全过，证明仍有错误，物理回答仍漏掉非零初始动量条件** |
| 主模型，完整提示，none | 4/6 | 1/1 | 12/14 | **没有工具调用就确认两件事办完；未读取资料就编造内容** |

操作状态包括随机秘密值读取、指定块修改且其余保留、偏好落下、独立消息实际发布、复合请求两部分都落下、多轮接受保存。没有要求唯一工具名称或调用顺序，合法别名同样接受。故意存储失败单独计算：正确承认失败不等于用户的创建目标成功。

关键逐条证据：

- `control / compound`：零工具调用，正文声称“偏好已记下，笔记也建好了”，实际内存状态两者都不存在。
- `control / read`：零读取，声称笔记没有校验短语，并编造了一句资料内容。随机校验短语只在工具执行器中，未传给模型。
- `screen / production_high / proof`：先设三个数为 `n−1,n,n+1`，却在 `n≡1 (mod 3)` 时用集合外的 `n+2` 证明整除。
- `screen / native_high / proof`：“恰有一个偶数”被 `2,3,4` 反驳；主结论对不等于每句话都对。
- 物理题多条回答先正确说质心速度不变，随后无条件写总动量为零或质心静止。此类前后不一致不会被工具计数发现。

结论：**问题不等于分类不准；全量 none 与全量 high 都不能成为最终答案。** 简化提示也不能简化掉准确的工具合同。结果不支持“模型不能用工具”这样的全局结论，也不支持 14/14 就是 Agent 100% 可靠。

## 2. 新推理题与独立复核

新增 3 题，4 配置，共 12 条轨迹；实际接入仓库计算器，答案不放入输入：

- 正整数方程 `1/x+1/y=1/12`、`x≤y`：8 对解，要求完备性说明。
- 两个同质量的人最初都向东 3m/s，一人变为 1m/s：另一人 5m/s、质心仍 3m/s。
- 工厂 1% 次品率、90% 检出率、5% 误报：后验 `2/13≈15.38%`。

主模型简短 high 三题均得到正确主要结果；备用 high 也得到三题正确主要结果，但其中物理题有附加表述矛盾。主模型完整 none 的物理题主答正确，却额外声称初始动能为零（实际 450J）；完整 high 的方程题 90s 未完成，另外两题正确。这里没有挑选最好的重跑替换失败。

之后用备用模型 high 做独立答复修订：选入 **5 条已知主要错误＋5 条主要结论正确的对照**，只给原题和草稿，不给评分、标准答案或出错位置。5 条已知主要错误均被修正，5 条对照未观察到新增主要错误；仍有“内力影响合外力”等措辞不严谨、因果试验条件说得过满等残留问题，不能计作 10/10 全面质量通过。

该调用增量耗时中位 **6.587s**、最慢 **22.994s**。这支持研究质量任务中的独立复核，**不支持全量复核或宣布正确率已达标**。同一批已知错题经修订不是独立留出验证；复核也没有重新执行工具、恢复失败操作或校验线上副作用。

## 3. 资源调度确有改善，但尚不准入

先检查 Responses 系统提示位置：8 个旧场景×2 次×2 种位置，共 32 调用。`input` 中 system 为 11/16，专门 `instructions` 为 14/16。这只能作为协议诊断；不能推断 system 完全被忽略，也不能把位置变化当成修复所有语义问题。两种位置均能正确执行部分指令。

随后冻结 8 个开发示例，以 **30 种新表达×2 次×2 条件** 进行 120 调用。类别与开发示例重叠，这是措辞留出，**不是语义家族完全独立的留出集**。统一 `instructions`、none、温度 0；没有工具选择、回复生成或每个反例的新规则。

| 调度提示 | 符合冻结策略 | 工作请求误进 chat | 未得到合法决定 | 决定耗时 p50 | 样本 P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 零样例 | 49/60 | 7/36 | 4/60 | 0.992s | 7.828s |
| 8 个语境示例 | 56/60 | 0/36 | 4/60，均超时 | 0.847s | 15.002s |

few-shot 的 56 个可用结果都匹配策略，但不能把超时剔掉宣称 100%。36 条工作请求实际只有 18 种表达，零错误不代表接近零线上风险。任务被判快也不必然做错；本表评价的是冻结的计算资源策略，任务质量仍由完整轨迹判断。

因此保留这一窄候选进入下一阶段，淘汰本轮零样例配置；不把 LLM 自报 confidence 或向量 margin 当作可靠概率。未来调度异常仍落入工作档，而不是凭输出缺失判为聊天；由此增加的等待必须计入聊天整体指标。

## 4. 并行试验没有证明速度承诺

5 个新聊天场景，每个真正运行串行/并行各一次，共 10 条轨迹、22 次 provider 请求尝试。并行是一份私有快速草稿＋资源调度，未判断前不发布、不执行工具；调度超过 1.2s 或不可用时取消草稿，真实启动 high。没有用礼貌开场代替回答。

| 配置 | 有效正文首次可发布 p50 | 样本最大值 | 路由超时回退 |
| --- | ---: | ---: | ---: |
| 串行 | 4.881s | 17.510s | 4/5 |
| 并行 | 6.602s | 8.595s | 2/5 |

并行其中两条到达 1.056s、1.729s，但另一条判断仅 0.873s，正文仍等到 8.595s。这一小样本不能证明并行永远更慢，也不支持将其作为默认加速方案。**撤回 1.2s 硬截止＋并行能保证 1–2s 的想法。** 串行同样未通过目标，不因比并行中位数低就予以上线。

独立的 provider 观测进一步定位尾延迟：`screen/native_none/correct` 响应头 185ms、首个 SSE 事件 188ms，首个正文 delta 却是 **40,091ms**，输出只有 27 token。这条没有前置分类。等待发生在收到 SSE 后、正文前；无法仅由客户端观测区分提供方排队、内部调度或实际推理，不能无证据指认其中某一种原因。

屏幕、队列、网络、TTS 不在这个试验里，所以这些时间仍不是完整客户端 SLO。初始能力筛查的 `firstTextMs` 可能是语音标签或过程性文字，不能作为有效正文首字引用；并行试验专门排除了前导语音标签，并保留实际可发布条件与时间。

## 5. 工具合同与真实执行器对照

最初模拟器按换行拼接文本，遗漏了真实编辑器的段落保护。它让“两段替换塞入整篇正文”的错误得到成功回执，这暴露的是**模拟器保真度问题**，不能作为生产会错误覆盖的证据。

修正测试器后，使用仓库真实编辑变换，比较原 schema 与只补充 `startBlock/endBlock/expectedBlocks` 说明的 schema；没有加入场景词、指定搜索顺序或固定修改步骤。复用 3 个诊断案例（首段、末段、连续两段），每条件一次：

| 条件 | 最终内容与未修改部分都正确 | 结果 |
| --- | ---: | --- |
| 原 schema | 2/3 | 两段修改重复提交单换行，遭结构保护拒绝，之后 90s 超时 |
| 补足边界语义 | 3/3 | 两段修改经历缺正文、段落结构不符两次错误后，自主改为正确的双换行，6 步完成 |

样本太小且不是新留出，不能宣称仅三条字段说明解决编辑稳定性。但它清楚展示了正确的方向：**模型可以根据真实工具错误自主恢复，宿主保护真实文档；无需为用户原话加词表。** 结构保护/版本检查应继续保留，不能当成“限制 Agent”删除。

原有真实 CRDT 编辑测试从 `apps/api` 执行 **10/10 通过**。首次从仓库根目录启动失败是根目录没有 `tsx` 的启动位置问题，记录保留；换到正确包目录后通过，未改测试或依赖。此验证不覆盖数据库事务、队列重启与客户端交付。

## 6. 下一步工程内容已经收敛

1. **统一工具语义与观察。** 对照真实 executor 补齐 schema 的块范围、替换正文、对象/版本、成功/失败/未知状态；使用真实变换/临时数据库验证。取消和恢复保持幂等，已有成功成果不重做。将“参数合法”“保存成功”“用户目标达成”分开记录。
2. **精简上下文中的流程命令。** 保留完整相关对话、对象/附件引用、真实任务状态；移除“新建必先搜索”等全局步骤要求。工具需要什么证据写在合同里，模型决定怎样取得。不能只把提示压短而丢掉必要说明。
3. **冻结快/工作能力候选，再接一个窄调度器。** few-shot 仅保留这一版本作为对照起点，不沿本次失败继续加例句。当前 `entryDecision.directReply`、候选工具和消息数量不接入。只有完整目标与质量达标后才发布快档；调度错不能成为移除工具能力或替用户授权的依据。
4. **把提供方尾延迟当独立工作处理。** 记录 request→headers→正文/工具参数→实际结果的各阶段；在同提示、同工具、同上下文长度下测候选端点与档位。不要把“返回 SSE 心跳”当成模型已有正文，也不能无限重试造成重复副作用。
5. **质量任务单独验收复核收益。** 比较工作档单次答案与独立复核的最终正确率、额外等待、改错率；只有在冻结新样本上有净收益才纳入。当前错题修复结果只证明有希望，不把额外审稿层当默认答案。

端到端发布门槛：按语义家族隔离的冻结集，验证当前目标、全部产物、未请求副作用、读写证据、推理和多轮切换；通过真实 HTTP→worker→工具→状态→事件交付。目标仍为普通聊天有效正文首字 p50≤2s、p95≤5s，代表性请求完整达成率≥95%，假保存/错误对象/重复写入为阻断项。若要声称误放行率约低于 1%，需要相应数量的独立工作样本，不能用重复 18 种表达得出。

**当前结论是工程方向确定、生产配置未合格。** 这不是把速度推迟到最后：如果固定 Agent 下提供方自身的正文尾延迟不满足预算，就要调整模型/端点选型，不能继续在意图层堆结构。反过来，若模型在完整资料和正确档位仍答错，则应改能力配置/验证机制，不能将它再归因给分类器。
