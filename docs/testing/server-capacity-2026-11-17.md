# Server capacity check — 2026-11-17

The production release tested was server 2.0.28 at commit `9b70f2cb0e7377200b79deb0e76d10b4c2909594`. The measurements below describe that release, not the uncommitted performance changes. The host had 8 vCPU and about 7.8 GiB of memory. These are workload-specific observations, not a user-capacity guarantee.

A 600-second test ran from 12:31:21 to 12:41:21 China Standard Time from a remote client over HTTPS. Four dedicated test accounts each had eight synthetic notes; the selected reader response was approximately 88,518 uncompressed bytes. Each account rotated among note list, cache version, workspaces, capabilities, and a note reader, waiting one second after each request. The tool created a new HTTP connection for each read and sent one AI turn per account at the beginning; it did not exercise uploads, voice, WebSockets, or sustained AI generation.

All 1,944 reads returned HTTP 200. Overall client-observed p50 was 213.5 ms and p95 was 336.9 ms; reader p95 was 344.3 ms. The compressed response bodies totaled 3,448,698 bytes, excluding headers and transport overhead. All four AI turns produced a final event; client-observed first delta was 4.35–7.30 seconds and final was 4.68–7.64 seconds. This is a short burst of four AI turns, not an AI throughput or p95 measurement. A sampled initial queue reached five pending and three running, and subsequently drained; this is not a continuous peak measurement. Test sessions were removed; the explicitly named test accounts and their content remain in the database. The local untracked evidence is `project-archive/performance/2026-11-17/mixed-4users-rerun.log`.

On November 16, a 6 MB upload from the server to Cloudflare's speed-test endpoint measured 9.28 Mbps. Four simultaneous uncompressed SSH transfers from the server to the test client measured 5.83–8.09 Mbps in two separate samples. These are path-specific samples, not an ongoing bandwidth guarantee. The production primary object store is remote; the standby MinIO is on the server and uses its public network when clients use the standby endpoint. Signed SHA-256 upload, checksum rejection and range-read prerequisites were verified on both stores with disposable objects.

An isolated, synthetic eight-iteration bcrypt benchmark on the production host compared the old JavaScript implementation and native asynchronous bcrypt. Median verification was 88.11 ms versus 70.85 ms; maximum extra delay to a 10 ms timer was 113.97 ms versus 0.59 ms. It did not measure complete login throughput, concurrent libuv pool contention or a deployed performance change. Legacy hash compatibility was tested separately in an Alpine container matching production.
