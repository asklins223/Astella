# 方案 57、58：解锁后的真实窗口检查与修复

2026-10-21，Asia/Shanghai。本记录接续[实施审计](./plan-57-58-audit-2026-10-21.md)。检查对象为本地 Electron 开发窗口和正在运行的 API、worker、Postgres；通过原生窗口操作检查，没有用 DOM 脚本代替交互。

## 当前结论

本轮发现并修复了放大布局、焦点、预览返回、恢复入口和只读请求误判。手记与学习卡的主要连续操作已实际走通。**方案 57、58 仍不能整体标记为验收完成**：题目语义一致性、真实模型质量与长会话稳定性仍有未闭环项目，见下文。

## 从真实窗口发现的运行链问题

固定请求为：“请根据《秦朝统一与中央集权制度》这篇已保存笔记，用三句话解释郡县制与分封制的区别；不要创建或修改笔记。”

1. “不要创建或修改笔记”仍触发编辑兜底，“已保存笔记”还触发新的保存请求。改为按分句识别肯定操作，否定、既有保存状态与引述不再被强制提升为写入。保留“不要改旧笔记，请新建一篇”等混合请求的肯定部分。
2. 明确点名笔记的读取请求仍先经过聊天前置模型，实测发生首输出超时。没有已预读正文时，现在直接进入既有解释器与任务链；已有宿主预读时保留快速回答路径。
3. 恢复后模型能够给出三句回答，却没有笔记读取回执，不能算依据原文完成。现沿用既有宿主预读：按完整标题查找当前用户可见、未删除的笔记，唯一命中才读取正文。重名、多个标题、不可见或缺失时不猜选对象。复用原文分页与版本读取，明确库内读取禁令和权限约束同样适用。
4. 真实手记中的同一句“方便面”闲聊来自四个不同的主动运行，不能由本轮重复校验拦截。发布前现在核对已存的交流，工具发言与最终正文使用同一判据；前台安静与学习开始的旧闲聊不会因为中间插入了用户消息而重新变成新内容。历史精确匹配在 SQL 中筛选，未增加一轮模型调用。真实启动／回前台问候、用户明确发起的回复保留原路径。仅检查原句／段落复读，不宣称能识别所有同义改写。
5. 主动运行的第一步没有装载发言与静默结束能力，导致模型先被拒绝，再多走一次装载。现按真实宿主主动机会准备这两项既有授权能力；不会补出宿主未提供的工具，也不增加笔记写入权限。隔离数据库验证了正常问候、新的有用补充、父回答复读、跨用户消息后的旧闲聊，保留无发言时的成功静默终态。
