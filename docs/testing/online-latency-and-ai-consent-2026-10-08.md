## 线上实测结论

用户报告正式客户端所有页面读取数据需 1–2 秒以上，插图更慢；服务器控制中心 p95 约 65 ms。从本机安装的 `/Applications/Astella.app/Contents/Resources/deployment.json` 确认生产 API 为 `https://103.106.191.159`，客户端版本 1.1.0。

使用同版本已安装客户端的独立测试进程，用户在临时窗口主动登录生产账号；只读测量账号可见的资料、笔记和设置。没有创建、修改或删除线上业务数据，临时登录目录已删除。生产账号实际为已签署、`sendToExternal=false`。

### 网络路径与直连对照

`route -n get` 显示目标走 `utun1024`，网关 `198.18.0.1`。Clash 控制器的连接记录确认，进程 `Astella` 的目标 API 流量命中 `Match`，最终走名为「美国洛杉矶集群」的节点。ping 平均 52.9 ms；Node HTTPS 复用连接样本为 344–355 ms，curl 样本为 439–473 ms。

相同目标的 Clash 延迟探测：DIRECT 首轮 64 ms，代理 343–458 ms；再次对照记录于 `outputs/online-latency-20261008/network-comparison.json`。此探测的 `delayMs` 与整个控制器调用的 `wallMs` 是不同指标。

用户明确同意加入单服务器规则 `IP-CIDR,103.106.191.159/32,DIRECT,no-resolve`。通过 Clash 的全局扩展脚本前置该规则，保留订阅原规则；控制器确认其位于索引 0、目标 DIRECT。仅关闭原目标 API 的旧代理连接以重新选路。应用后重新测同一个 HTTPS：252、200、113、67、64、66 ms，冷连接与稳定连接分别保留。证据见 `outputs/online-latency-20261008/after-direct.json`。

正式客户端随后通过真实侧栏打开笔记库，加载状态退出、真实笔记和版本出现。没有给此次 UI 操作建立可靠的逐帧总耗时记录，因此不把接口的 64–67 ms 声称为整页打开耗时。

当前线上笔记样本没有被测脚本识别出的站内对象图片，未取得图片大文件下载、上传与带宽的线上对照。对象存储本身不能消除绕路或串行请求；此次只修改 API 的路由规则，没有扩大到对象存储域名。

## 代码修复

- 签署接口在同一事务内保存签署并开启 `sendToExternal`；新账号沿用数据库默认策略，既有账号保留图片、PII 检测和审计选择。读取不授权，用户之后主动关闭的选择不会自动重开，没有批量迁移历史关闭状态。
- 首次指引同时核对签署和外发总开关，成功回执也必须确认外发已开启；协议文案明确同意后会开启外部 AI。已有签署但关闭外发的账号可以主动再次确认。
- 聊天发送前分别说明缺签署和外发关闭；worker 在执行前及执行期间将策略拒绝归为 `AI_DATA_POLICY_DENIED`。语音门禁也核对总开关，经 IPC 映射为具体错误，避免反复重试合成。
- 页面复用门禁核验过的账号、空间和纪元，减少每次导航前的 `/auth/me` 串行等待；门禁失效即清理，实际 API 的会话、权限与 main 的纪元校验继续生效。
- 已选笔记的正文、首页与能力同时读取；来源、任务、目标、订阅和学习记录按笔记身份并发读取，教学内容仍等待真实轮次。首页数据与能力/恢复信息并发，能力的在途请求按身份和失效代次合并。
- 并发读取共享同一请求的取消控制，直到所有子读取结束才释放；页面卸载和换目标后，旧读取不能发布结果。
- 插图在服务端确认保存原文件之后复用本机文件显示，避免立刻重新下载刚上传的图片。blob 缓存按部署、账号、工作区纪元隔离，门禁失效时清理。
