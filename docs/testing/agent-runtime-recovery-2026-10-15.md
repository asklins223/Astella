# Desktop Agent working-state recovery — 2026-10-15

This review covers the desktop client and its dependent API/worker chain. Mobile is excluded by the user's latest decision. The review goal remains active; the remaining acceptance work below is not waived by passing tests.

## Changes

A restarted Agent previously reconstructed the frozen base prompt but lost the accumulated tool transcript, format-correction feedback and used repair allowances. Migration `0440_companion_runtime_recovery.sql` adds private `runtime_checkpoint` and `result_payload` columns to the existing scoped step/tool ledgers. The running-step input, continued state and settled result are schema/hash-bound to the exact run, committed base messages, current request, permission, tool definitions and provider configuration. Complete tool results are committed with the succeeded ledger transition. Neither field is part of public diagnostics or user history. One complete current runtime state is retained; advancing to a new input clears older copies. Original history and tool source remain intact; there is no hard truncation.

Recovery restores complete tool messages, compaction evidence, visible segments and delivery flags, rich blocks, elapsed execution time, search counts and correction/no-progress state. A settled result finishes without another model request. Committed visible deltas are reloaded with strict append-offset verification. A partial stream without a complete model result keeps its already delivered prefix and reattaches the original current request with explicit interruption feedback. A matching complete model checkpoint is reused without replaying its delivered text.

Confirmation now has a distinct private waiting checkpoint, committed in the same transaction that publishes the card. A quick decision cannot observe a card without its full paused state. It retains the entire native tool batch, earlier tool results and the pending proposal/call identities. Each later call receives an explicit `not_executed` receipt with its original arguments retained in the assistant tool batch. After a real decision, the decided receipt is replaced in place; earlier reads are not reconstructed from a short summary. The model can continue the remaining work using those receipts. Confirmed result data and result blocks are restored from the actual ledger; a rejection does not execute the write. Pre-0440 proposals without private state retain the existing continuation path.

Lease fencing was also incomplete on failure bookkeeping. Step creation/completion, runtime metadata, tool-event publication and run failure now verify the job lease under the run-first lock order. A timed-out owner may record its failure while its lease remains current; a replaced worker cannot close the new owner's step or publish an error over its run. The PostgreSQL test replaces a lease during a real handler call, verifies unchanged live state after the old exception, and then completes with the replacement owner. Mixed-batch tests also keep the original job lease live during API-equivalent continuation binding and verify that old metadata/events/failure bookkeeping cannot regress the accepted continuation.

A subsequent ledger review added run/job/lease ownership checks to tool registration, rejected-call audit writes and status transitions. A refused transition to `executing` cannot reach the business operation. A succeeded receipt and its confirmed proposal now commit together. Identical writes rejected by the user are reused as `not_executed` even if the provider changes its call ID; the rejection cannot be bypassed by another card in the same run. A new user turn remains a separate run.

Failure bookkeeping has a distinct transaction guard. The current job may record a failure after its source or account permission becomes invalid, and after its own abort signal fires. It still verifies the run, generation, frozen account epoch, current job binding and immutable job lease. It cannot execute a tool, publish success, or write over a replacement owner. Recovery/input/success paths continue to require current source and account authorization.

Initial thinking publication and final answer delivery now lock the run before the job lease and verify the current job/account generation. A PostgreSQL fault hook changes the lease at the settled-checkpoint boundary: the obsolete process is refused final publication, and a replacement consumes the complete saved result without another model call.

## Native confirmation and desktop polling regression

The actual Electron client submitted run `af591374-9a1f-465e-aa75-50665ca7f55f` using the configured real MiMo provider and ordinary production platform configuration, against isolated PostgreSQL. The model prepared a `companion_create_note` confirmation card containing all five corrected facts. The card and full waiting checkpoint were committed before user interaction. The desktop client was restarted while the card was pending; no second user submission or status reset was used. The native Save button confirmed proposal `94cb3edc-e7ff-4454-94fd-d9ead747109a`. The same run resumed and displayed the correct final one-line answer. Its navigation button opened the actual note. The database contains exactly one note and one version, with the correct full body and unchanged original history hash. The native note briefly showed its document-initialization save state before settling to the acknowledged saved state; it did not create another note version.

This check exposed a real desktop request storm. After ten seconds without an SSE frame, the old fallback permanently switched to 300 ms history polling; background node/route reads also ran every 1.6 seconds. In the observed 22:56:00–22:57:00 local window there were 190 message reads, 60 node reads, 38 route reads and 171 HTTP 429 responses across companion routes. The shared companion read quota is 120 per minute. The resulting rate limit prevented the confirmation card from loading.

The desktop now uses serial fallback reads, settling at five-second idle intervals. A silent stream requests one prompt check without changing into a permanent fast loop. Supplemental reads run at five-second intervals, cannot overlap, and survive conversation-object identity changes without restarting their schedules. Failed reads back off; server Retry-After deadlines remain effective even when a stream requests a prompt check. SSE still delivers first tokens immediately, and polling does not impose a fixed execution timeout or truncate any content.

After rebuilding and restarting the native client, the 23:05:10–23:06:10 window included opening the pending card, saving, receiving the final answer and opening the note. It contained six message reads, nine node reads, six route reads and no HTTP 429 responses. These windows demonstrate the observed regression and its repair; they are different interaction sequences and are not a controlled latency benchmark. Desktop type checking/build and 26 relevant tests pass, including two minutes of silent SSE, cancellation during an in-flight read, Retry-After and terminal-answer recovery.

Artifacts under the task's `outputs/`: `agent-native-confirmation-recovery.json` and `agent-native-desktop-polling.json`. The first-delta interval of the confirmation run includes the deliberate wait for confirmation and rebuilding/restarting the client; it is not a model speed measurement.
