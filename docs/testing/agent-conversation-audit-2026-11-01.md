# Agent 日常对话、稳定性与 iOS 过程展示复查

2026-11-01，Asia/Shanghai。结论：服务可用，但日常对话体验还不稳定。当前有可重复的交付缺陷、普遍的额外模型补跑，以及人格里的行为复盘干扰表达。不能用 `succeeded` 或单测通过代表“说得好、交付完整”。

本轮完成调查、真实模型实测和复现，未修改业务实现、用户人格或生产配置，未执行部署。

## 范围与证据口径

- 真实 HTTP → 队列 → worker → 配置中的真实模型 → SSE 与数据库交叉核对。两组连续十轮对话，线上、本地各跑一次，共 **40 轮**。包括招呼、生活分享、短确认、疲惫、纠正、换话题、简单知识问答、告别。
- 另在本地隔离账号中复制线上人格，再做“完整人格 / 只移除自我描述”各四轮探索性对照，**8 轮**。总计 **48 轮**，这八轮不混入主对照的速度统计。
- 读取线上近期运行记录、步骤错误、模型调用元数据，以及与用户反馈直接相关的对话和人格版本。未改真实账号历史或偏好。
- 用一条真实本地 SSE 回合调用 iOS 的 `replySections`，复现消息/过程投影。属于 Swift 数据投影验证，**没有进行 iPhone 真机或模拟器触控验收**。
- 相关现有 worker 测试 **148/148 通过**。这与下文缺陷同时成立，说明现有测试未覆盖真实交付一致性。

线上第一组开始时运行 `2.0.15 / 53d360d7`；调查期间约 13:15，另一条发布流程将线上更新为 `2.0.16 / e6dab981`，第二组在更新后执行。本轮没有触发该发布。本地是 `e6dab981`，API/worker 挂载当前源码。两版本在本轮涉及的对话 runtime、人格与交付链代码没有差异，worker 的相关版本差异是笔记来源解析。

原始证据放在忽略目录 `outputs/audits/2026-11-01-agent-review/`。其中真实账号人格、对话及带思考原文的回放仅供本地排查，不复制进可提交材料。可复核的合成账号对话与统计：

## 稳定性和速度

| 口径 | 本地，20 轮 | 线上，20 轮 |
| --- | ---: | ---: |
| 后台标记成功 | 20/20 | 20/20 |
| 首条可见正文，中位数 | 1.88 秒 | 1.73 秒 |
| 整轮结束，中位数 | 6.24 秒 | 7.82 秒 |
| 最慢首条可见正文 | 8.89 秒 | 9.43 秒 |
| 最慢整轮结束 | 10.22 秒 | 18.49 秒 |
| 队列等待，中位数 | 0.10 秒 | 0.12 秒 |
| 触发 `FINISH_CONTRACT_INCOMPLETE` 的回合 | 20/20 | 20/20 |
| SSE 正文与落库正文不一致 | 1/20 | 5/20 |
| 正文后仍出现思考/工具事件 | 18/20 | 20/20 |

首字取服务端运行建立到第一条持久 `assistant.delta/utterance` 的时间，另留客户端 SSE 接收时间；只按当前 runId 匹配，不把旧事件回放计入首字。终态取 `finished_at-created_at`。这些是小样本对话观察，不能当线上长期 P95/SLA。

主要等待发生在模型与交付补跑，队列不是这组样本的主要瓶颈。初始正常回复被要求补跑后，后续步骤耗时中位数本地约 2.74 秒、线上约 4.03 秒；这是观察到的后续步骤时间，不保证修改后能原样全部省去。极短的“嗯”也可能等约九秒才出正文。

40 轮中记录到 90 次主对话链 provider 调用，其中 50 次走备用模型。`run.model_id` 通常仍标记主模型 MiMo，不能据此认定整条回复只由它生成。`model_call_count` 还可能包含异步后续问题建议，评估回复成本和延迟时应分开统计。

线上 `/health`、`/ready` 正常；最新 API/worker 健康且 restartCount=0。七天记录中，排除 `@test.invalid` 账号后，用户发起回合有 37 条成功、1 条首输出超时、4 条取消；跨越多个版本且样本有限。不能把取消统一算故障，也不能据这些数据宣布已经长期稳定。另发现终态为 superseded/cancelled 的回合仍留有 running 步骤，应补终态收敛，避免诊断与客户端过程状态失真。

## P1：普通聊天每轮被迫补一遍结束协议

`companion-agent-runtime.ts:1075` 使用完整 `definitions` 判断有没有可写/可交付工具。这个判断反映账号拥有的能力，不代表本轮用户要求做操作，也不完全等同于本步真正呈现的工具面。

当模型先正常回答、没有发出工具调用时，代码要求再调用 `companion_finish`，记录 `FINISH_CONTRACT_INCOMPLETE`，并设置 `steerSwapToFallback=true`。在本次 40 轮中，这条链每轮都发生。主模型已说出的文字之后，备用 DeepSeek 又被要求核对并交付，增加等待，也给改口、重述和风格切换创造了机会。

更具体的交付漏洞：这条分支在 `:1090` 返回 `continue`，而登记 `visibleSegments` 在 `:1098` 才发生。已经经 SSE 发出的正文可能没有进入 runtime 自己的可见正文账本。后续重试可能从头说，拼接时还缺段间分隔；最终组装文本与真实 SSE 因而分叉。

实测例子：一个招呼产生“下午好呀……下午好。饭点刚过……”两段重复问候。线上“随便聊两句”的回合则把第一段闲聊和第二段改写直接接起来，最终用了 18.49 秒。

修复方向：

1. 先把已经公开的正文登记到唯一交付账本，再进入任何重试/恢复分支；恢复时必须携带公开状态，不能把已发布回答当新草稿改写。
2. 将正文与结束声明设计为同一次正常模型调用可完成的协议。真实操作仍必须引用真实回执，避免为了聊天提速撤掉执行真实性检查。
3. 普通回答是否需要补充合同，不能由“全目录含有写工具”推出；按结构化交付类型、本轮动作及回执校验。不要重新堆用户措辞词表，也不要增加一层语义审查来改写口气。
4. 单纯结束元数据不完整，不应自动触发跨模型重新生成正文。跨模型恢复保留给真实协议/供应商故障等必要情形。

## P1：已经流出来的尾字在历史中消失，但仍然成功

主对照 **6/40** 存在 SSE 完整正文与 `companion_messages` 文本不一致。其中两条只差最后句号，四条丢失正文尾词。所有 SSE 的 `appendFrom` 连续，没有断流缺段证据。

| 场景 | 实际 SSE 尾部 | 保存的尾部 |
| --- | --- | --- |
| 本地招呼 | “我这边也正闲着，聊点什么？” | “我这边也正闲着，聊” |
| 线上不安排事情 | “我就随口一说，不催你。” | “我就随口一说，不” |
| 线上分享 | “这个画面今天算是赖在我这儿不走了。” | “这个画面今天算是赖在我这儿” |
| 线上纠正 | “改成你轻轻喊了一声。” | “改成你轻轻喊” |

`companion-dialogue.ts:1180` 在 `streamingDelivery.finish()` **之前**保存 `alreadyDelivered` 和降级前缀；`:1188` 才把节流队列的尾部刷出。如果随后全文对账失败，`:1246` 使用的还是 flush 前的旧快照。于是客户端与 TTS 已经接到尾字，数据库与 `assistant.final.textLength` 却回到较短文本。

这不只是句子风格。它会让实时画面、重进历史、语音以及下一轮模型读取的历史彼此不同。

修复方向：以 flush 后实际持久交付的文字作为最终核对基准；统一 runtime、SSE、落库正文、语音区间与 final 哈希的来源。保留可用的部分结果，但把降级明确记入交付状态，不能仅凭“有非空前缀”就把半句话当完整成功。

验收必须覆盖：尾部留在节流窗口时进入 finish、正文已发后纠正、换备用模型、SSE 重连、失败恢复。应断言重放出的可见文本、最终消息和 final 哈希一致；不能只检查 `status=succeeded` 和消息非空。

## P1：iOS 的“消息下面显示思考与过程”已经复现

真实回放输出：

```text
sections = [
  [body(41)],
  [思考与过程(companion_finish), body(4)]
]
savedChars = 41
visibleChars = 45
```

因果链：

1. 服务端先流正文，后因结束合同补跑思考，最后发 `agent.tool / companion_finish`。
2. `CompanionRecordPresentation.swift:236` 按事件时间顺序，将任何 thinking/tool 切成一个过程段；正文后的控制事件也切段。
3. `MessageHistory.swift:433` 直接依次渲染 section.parts，因此新过程自然出现在已有气泡下面，甚至把最后几个字另分成一个正文片段。
4. `CompanionRecordPresentation.swift:278` 对单条已保存消息仍保留 SSE 派生的文本，不用保存正文替代，所以它会继续呈现与服务器历史不同的那份文字。

建议把对话正文和执行详情分开投影：一个 run 有稳定的过程入口，默认收起，放在回复级别；正文气泡只由真实消息边界决定。`companion_finish` 这类内部控制收尾不要作为用户操作项。工具成果、待确认操作、真实错误仍保留明确位置；完整时序可留在展开详情，不能简单把所有事件排序搬到最前面，破坏工具与成果的关系。

这轮只是确认根因和提出方案，没有改 iOS 样式或排序。修复后需要真机覆盖流式完成、回到历史、分条发言、需要确认的操作、取消/重连，不能以这一个 Swift 回放替代界面验收。

## P1/P2：人格里混入了主动发言复盘，聊天容易变成表态

线上找到与反馈对应的真实链条：用户只是叫“小肥鱼”，回答却是“在呢。忙你的，我不吵。”；用户说并没有嫌它吵，它又解释自己上一轮如何说话，并收尾“有话说话，没话也不硬凑”。它把主动参与上的克制，泛化成了当前用户不想被打扰。

线上人格 revision 7 的 `selfDescription` 含多段模型写下的复盘，例如“话省着用”“没有回音的主动消息不硬补”“别只靠自觉”。还有过去主动消息过多、反复追问的事故经过。这些材料会随人格进入普通对话；行为经验和性格混在一起，模型容易不断宣告自己会克制、不会催、不会硬聊。

当前 V14 的通用风格其实已经写了“不要讲自己正在如何接话”“不要把用户约束复述成承诺清单”。继续加同类禁令的收益有限。需要处理同时存在的竞争上下文与重试改写。

隔离账号也复现了几种口气问题：

- 被说像客服后答“行，那我正常说……一随便就容易端着，反而不知道怎么说话了”，仍然围绕“自己如何说话”解释。
- 用户说不用反复强调，它又回“行，记下了。那我以后就直接接话，不绕那些”。
- 前面一只“土豆猫”的梗被拉回多轮，连告别仍加“土豆猫我先替你收着”。有了可用素材就反复使用，缺少当前这句是否还需要它的判断。
- 分享后的回应常变成“这个描述太准了”“太有画面感了”加一遍扩写；细节与玩笑有时有效，但容易变成固定结构。
- 收尾还习惯补小建议，比如洗澡前提示水温、躺了一下午后追问晚饭。

也有正常表现：能接住纸箱猫的笑点；冰浮在水上的问题能按两句话回答；大多数告别没有启动工具任务。所以不能简单说完全不会聊天。

人格探索对照共八轮：保留完整线上人格时，会说“躺一下午还能心安理得，这本事不是谁都有的”，再问晚饭；只移除自我描述时，对同一句变成简短回应，没有继续追问。这个变化支持分离自我复盘值得尝试，但**每条件仅四轮、模型随机性未控制、未复制全部用户历史，不能证明删自我描述就一定解决问题**。本轮没有删除真实账号任何内容。

建议：保留用户选择的名字、性格、口味、示例；将模型自生的事故复盘、主动参与频率经验放入带适用范围的行为记录，按触发场景使用，不常驻人格正文。“主动消息无人回应”应是参与策略的证据，不能变成“用户嫌我吵”的事实。用户主动开口时，以当前一句为准。

表达调优应看连续对话是否接得住、有没有增添具体意思、是否反复自我说明，以及何时该自然结束；不要机械限定每轮字数、禁用一串词、强塞语气词，也不要统一改成冷淡短答。知识回答质量需要独立核对，本轮没有给出系统性知识正确率；咖啡题中关于温度、酸味、苦味的机制解释尚需事实复核，不能因回答流畅就记为正确。

## 建议实施顺序与验收

| 批次 | 改什么 | 必须证明什么 |
| --- | --- | --- |
| 1 | 交付账本、flush 后对账、正文后的恢复行为、正常结束协议 | SSE/历史/final 哈希一致；普通短聊不再每轮产生 FINISH_CONTRACT_INCOMPLETE；真实写入与产物仍须回执 |
| 2 | iOS 回复级过程入口、内部控制事件展示规则、消息身份 | 普通回复末尾无内部思考/finish 尾巴；单条正文不因过程事件切断；真实分条、成果和确认卡不丢不重 |
| 3 | 人格和参与经验分离、修正历史误解的适用范围 | 用真实人格与长历史复测；不再把克制当每轮口号；不把用户未说过的意图补出来 |
| 4 | 上下文与时延优化、观测指标完善 | 单独统计首字、正文完成、run 完成、额外模型调用；后台建议与交互回复分账；不能用降低任务可靠性换速度 |

先完成前两批，再评价风格改动，避免用户实际听到的仍是两个模型接力改写后的拼接稿。修复后的同组对话应重复运行，并增加真实人格/长历史、短确认、结束话题和显式行动交叉场景；人工逐轮审读和跨层交付断言都要保留。
