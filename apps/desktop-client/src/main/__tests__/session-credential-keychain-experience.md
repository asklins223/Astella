# macOS 启动钥匙串弹窗修复（2026-10-08）

现场旧记录 `astella-desktop-client Safe Storage` 的受信应用是开发依赖里的
`Electron.app`，分区绑定开发版的 CDHash。安装版 `/Applications/Astella.app`
共用同一个 package name，但签名不同。用户每次拒绝，下一次启动又会访问该记录。
启动日志在 IPC 注册之前停留约 20 秒，调用入口是凭据存储构造时的
`safeStorage.isEncryptionAvailable()`，当时尚未创建主窗口。

安装版在 `ready` 前设置独立的 `Astella` 应用名，并保留原来的 userData 路径。
macOS 安装版使用 `session-credential-packaged-v2.bin`，开发版继续使用原文件；
不读取无法通过新钥匙串身份解密的旧凭据，迁移后用户登录一次。
快照、构造、无凭据的恢复与清理都不调用安全存储；用户选择保持登录后才加密保存。
保存失败必须抛错，让网关正确记录为内存会话，不能虚报已持久化。

验证：

- 凭据存储、应用身份与真实网关回归共 109 项通过；桌面端 `npm run typecheck` 通过。
- 完整桌面构建、房间资源守卫、安装包深度签名校验通过。
- 原有两版本更新签名兼容及损坏资源拒绝回归通过。
- 在签名安装包的主进程中运行实际凭据模块，使用隔离目录和测试令牌：
  加密保存后确认文件权限 0600 且不含明文，退出进程后再次启动、恢复并清理成功；
  两个进程全程无授权交互，应用名为 Astella，原启动配置目录保持一致。
- 更新 `/Applications/Astella.app` 后，真实窗口正常启动且无钥匙串弹窗；
  保留旧安装包的 deployment.json 后服务连接正常，用户自行登录并进入原书房。
  登录凭据已以 0600 权限写入新文件。用户正在操作真实窗口，最终没有强制重启
  该会话；跨进程恢复证据来自上述同签名安装包的隔离凭据验证。

正式发布仍应使用一致的 Developer ID 签名。ad-hoc 的跨版本更新要求通过，
不代表 macOS 钥匙串的 CDHash 分区会自动跨构建授权；此修复解决开发版与安装版
共享记录以及无条件启动访问的问题，不扩大旧记录的受信范围。
